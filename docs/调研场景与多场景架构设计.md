# 调研场景与多场景架构设计（草案）

2026-10-27，基于与 Sean 的设计讨论整理。海报 PoC 已跑通（见《黑五海报PoC技术方案》），本稿回答两个问题：三个场景如何共用一套底座；调研场景具体怎么设计。只谈设计，实现另起。

## 1. 已定的三个原则

这三条是讨论里定下来的，后面所有设计都从这里推：

1. **场景之间不切换，只传"确认物"**。调研的最终结果既是交付物，也是下一个线程的输入。一个线程只做一个场景；PPT 或海报新建线程时从某个已导出的包里导入，导入的内容带"已确认"状态。不做"一个线程里从调研切到 PPT"，那样会混淆模型，业务也难维护。
2. **确认点分两类**。返工成本高、每次都该停的，写死在流程图里；结果本身比较确定、用户看个摘要就行的，不问；模糊或模型判定需要人介入的，由 agent 在循环中主动提问。两类并存，机制不同。
3. **调研先行**。三个场景顺序都可以，但调研最需要模型自主调用工具，先做能一次验证掉工具调用、来源追溯和 agent 嵌入固定流程这三件事。

## 2. 分层：外层固定流程，内层 agent

```
场景流程图（StateGraph，每场景一张）
  ├─ 固定确认点：interrupt()，位置写死
  ├─ 确定性节点：按已确认内容生成 / 渲染 / 校验
  └─ agent 节点：create_agent 子图，只在"模型要自己决定做几步"的地方出现
        └─ 内含"问用户"工具 → 动态确认点
```

- **外层**负责"人在哪些点介入"。这一层不让模型决定流程，确认点必须稳定可预期。海报现在就是这样，不改。
- **内层** agent 是外层的一个节点，进出口受外层控制：输入是已确认的范围和大纲，输出是候选来源和候选论断，不直接产出交付物。
- 海报目前没有 agent 节点；调研的"搜与读"是第一个；PPT 可能有一小块（按大纲去用户材料里找支撑）。

和 `create_react_agent` 的关系：它在 langgraph 1.x 已标弃用，统一用 `langchain.agents.create_agent`，为此引入 `langchain` 主包（1.x 主包只剩 agent 与 middleware，很薄）。**不自己手写 ReAct 循环**（2026-10-27 Sean 定）：循环交给 `create_agent`，我们只写工具、提示词和把它挂进外层流程图这三样。海报 PoC 没引入是有意的，海报没有需要模型自主调工具的环节。

## 3. 三个场景共用的底座

### 3.1 已确认内容是一等公民

海报里叫事实绑定和元素状态机。推广到三个场景：

| 场景 | 已确认内容 | 模型的权限 |
|---|---|---|
| 海报 | 事实、元素、风格 | 只写未锁定槽位 |
| 调研 | 来源、论断、大纲 | 大纲确认后只能往里填；论断确认后不改；来源排除后不引 |
| PPT | 大纲、已定稿的页、引用的论断 | 改一页不动其他页 |

统一的状态机沿用海报那套：`draft → confirmed → user_edited`，`user_edited` 模型以后不碰；模型要改 `confirmed` 必须显式重开（用户点名），不能顺手改。

### 3.2 提问是统一的交互原语

前端已经把海报的三种中断做成"问题卡"。往后所有确认点都走同一种卡，只是题型不同。后端 interrupt 的 payload 先定格式，场景只填内容：

```
{
  "type": "<场景>.<确认点>",      # 如 research.scope / research.outline / research.ask
  "title": "...",
  "questions": [ {key, label, kind: single|multi|text|confirm, options?, default?, required} ],
  "context": {...}                 # 给卡片展示的辅助信息（候选来源、当前大纲…）
  "why": "..."                     # 动态提问必填：不问会怎样
}
```

`kind` 和 MCP elicitation 的扁平 schema 对齐（单选 / 多选 / 文本 / 确认），响应三态：回答 / 跳过 / 取消。

### 3.3 交付物可追溯，且交付物 = 确认物包

每个场景导出的都是一个包，不只是一个文件：

```
package/
  manifest.json      # 场景、线程、版本、导出时间
  deliverable.*      # 报告 .md / 海报 .png+.html / 演示 .pptx
  items.json         # 已确认内容清单：id、kind、content、status、provenance
  sources.json       # 来源（调研有；海报 / PPT 引用时带过来）
```

`items.json` 是跨场景流动的唯一格式。海报的事实、调研的论断、PPT 的页，都是一条 item，字段统一：`id / kind / content / status / provenance / source_ids`。下一个线程导入时，item 直接进 state，状态保持 `confirmed`，`provenance` 指回原包。

## 4. 调研场景流程与确认点

```
intake ──► [范围确认] ──► plan ──► research_agent ──► [大纲确认] ──► write ──► check ──► [终审] ──► export
   ▲                                   │                                           │
   │                                   └── 动态提问（ask_user 工具）◄──┐            │
   │                                                                   │            │
   └──────────────── 修改范围 ◄────────────────────────────────────────┴────────────┘
```

### 4.1 固定确认点（三个）

| 确认点 | 问什么 | 为什么必须停 |
|---|---|---|
| 范围确认 | 研究问题的一句话表述；边界（时间、地域、语言、信源偏好）；不研究什么；交付形式 | 范围错了整轮白搜，返工成本最高 |
| 大纲确认 | 章节结构；每章要回答的问题；各章已有的候选论断摘要 | 结构定了正文才能逐节生成；这是调研类产品公认的唯一硬确认点 |
| 终审 | 逐节看报告；排除来源 / 改论断 / 改措辞；导出 | 和海报 review 同构 |

范围确认和海报的事实确认一样是"一题一页"，有推荐默认值，用户可以"直接开始"跳过（Kimi、OpenAI 都这么做）。

### 4.2 动态确认点

给 research_agent 一个 `ask_user` 工具，提示词规定**必须**问的情形：

- 术语或实体有歧义，不同解释会导向不同的搜索方向
- 两个可信来源互相矛盾，且矛盾影响结论
- 发现问题比用户说的更大或更小，需要收窄 / 扩大范围
- 连续几轮都找不到可信来源，要确认是否降低信源要求或放弃该分支

两道闸防止问得太勤：

- 每轮调研 `ask_user` 调用次数上限（初值 3 次）
- 每次提问必须填 `why`（不问会怎样）；填不出来就不许问，由模型自己判定并在摘要里标注"此处按 X 假设处理"

不在"必须问"清单里、又确定性足够的，模型不问，只在交付物的"假设与取舍"一节列出来。用户之后要改，走终审。

参考 Notion 的做法，这个频率将来可做成用户设置（每步确认 / 关键处确认 / 不打扰），PoC 阶段先固定为"关键处确认"。

## 5. 调研场景 state

```
ResearchState
  request            原始需求
  scope              范围（确认后锁定）：question, boundaries{time,region,lang}, exclude[], deliverable
  outline            大纲节点列表，每个节点：id, title, question, status, claim_ids[]
  sources            来源列表
  claims             论断列表
  assumptions        模型自行处理的取舍记录（没问用户的那些）
  report             正文，按大纲节点分段，每段挂 claim_ids
  versions           每轮终审一版
  checks             校验结果
  asks_used          本轮动态提问计数
  exported           包路径
```

### 5.1 来源 Source

```
id, url, title, retrieved_at, excerpt（引用原文片段）, status: candidate | adopted | excluded, note
```

状态由用户决定（终审或大纲确认时），模型只能提候选。`excluded` 的来源不得再被引用。

### 5.2 论断 Claim

```
id, statement, kind: fact | inference, source_ids[]（≥1，必须都是 adopted）,
status: draft | confirmed | user_edited, outline_id, confidence: high | medium | low
```

- `kind` 放进 schema 里强制模型二选一，不让它在措辞里含混。这是上一轮调研评审反复指出的问题。
- `source_ids` 为空的论断不允许进报告。
- 来源被排除时，依赖它的论断自动降为 `draft` 并标出，不悄悄保留。

### 5.3 大纲 Outline

确认后结构锁定：模型不能增删章节，只能往 `claim_ids` 里填。用户在终审可以重开大纲，重开后已确认的论断保留，只是重新归章。

## 6. research_agent 的边界

它能做的：

- 搜索（web search 工具）、抓取与阅读（fetch 工具）、从页面里提炼候选来源和候选论断、调用 `ask_user`
- 按大纲节点分配搜索，每个节点独立预算

它不能做的：

- 不写报告正文。正文由 `write` 节点按已确认大纲和论断逐节生成，每句话回指论断，这样才能追溯。
- 不决定大纲。它只产出候选大纲，交固定确认点。
- 不改任何 `confirmed` / `user_edited` 的东西。

硬上限：总搜索轮数、每节点来源数、`ask_user` 次数。超限停下来交用户，不自行放宽。

## 7. 校验（确定性，不靠模型）

和海报的 `checks.py` 同构：

| 校验 | 规则 |
|---|---|
| 论断有据 | 每条进报告的论断 `source_ids` 非空且全部 `adopted` |
| 事实 / 推断可辨 | 报告正文里推断类论断带可见标记（如"推断："或脚注） |
| 来源可达 | 导出时每个 adopted 来源的 url、标题、抓取时间齐全 |
| 排除传播 | 没有任何论断引用 `excluded` 来源 |
| 范围一致 | 报告涉及的时间 / 地域不越出 scope（粗校验，关键词级） |

## 8. 验收标准

对应海报的三条，调研定这三条：

1. **每条结论都能点回来源**。报告里任意一句论断，能定位到 claim，再定位到 adopted 来源和原文片段。
2. **事实和推断在报告里看得出区别**。读者不用问模型就知道哪句是查到的、哪句是推出来的。
3. **排除一个来源，依赖它的论断会被标出而不是悄悄保留**。用户在终审排除来源后，受影响的论断回到草稿并在界面上可见，重新生成只动这些论断。

额外一条验证本次架构：**调研包能被海报线程导入**。从调研包里挑一条事实型论断作为海报的事实，海报线程里它带 `confirmed` 状态且 provenance 指回调研包。

## 9. 验证案例

题目用我们自己的：**"AI 海报 / PPT 工具在局部修改和事实准确性上的现状（2026）"**。

选它的原因：我们真正想知道答案；`reports/WorkBuddy 与同类产品调研.md` 是现成的对照，可以比较 agent 版和之前人肉协调版的来源质量与结论差异；结果能直接喂给后面的 PPT 场景（给团队汇报用）。

预期走法：范围确认（时间限 2026、中英文都要、排除纯营销稿）→ agent 分章节搜 → 大纲确认（预计 4～5 章）→ 终审时故意排除一个来源看论断降级 → 导出包 → 新建海报线程导入一条事实。

## 11. 风险

- **豆包的工具调用与 strict json_schema 是否兼容** `create_agent`。海报用的是结构化输出，不是 function calling；需要第一步就实测。
- **中文信源抓取**。公众号等无官方 API，fetch 工具可能拿不到正文；PoC 先接受"拿不到就不引"。
- **agent 质量不可控**。搜索轮数、来源筛选质量都依赖模型；硬上限和校验兜底，但报告质量本身不是 PoC 的验收目标。
- **包格式过早固化**。`items.json` 只在调研→海报这一条路径上验证过，PPT 接入时可能要调整，先不求完备。

## 12. 技术栈核实（2026-10-27）

动手前查过的事实，供第 13 节选型用：

**方舟联网搜索**（文档 `docs.volcengine.com/docs/ark/web-search`，2026-10-27 版）

- 两个工具：豆包搜索 Custom 版（推荐）和联网内容插件，类型都是 `web_search`，都是**服务端工具**：模型在一次调用里自己搜、自己读、自己答，返回的是答案文本加 `url_citation` 注释（title、url、site_name、publish_time、summary），不是原始结果列表。
- Custom 版支持 Responses / Chat / Messages 三种协议；联网内容插件只支持 Responses。
- **Chat Completions 下自定义 function 工具和 `web_search_options` 不能共存**，同时传只执行自定义工具。Responses 下 Custom 版可与 function calling 组合。
- `max_tool_calls` 限制一次响应里的搜索轮次，默认 3，范围 1～10。不能与 `caching` 同用。
- 使用前必须在控制台「应用组件库 > 豆包搜索」开通 Custom 版，按豆包搜索产品计费。
- 官方建议：Agent 场景把联网搜索单独封装成 subagent，由主 Agent 编排。

**LangChain `HumanInTheLoopMiddleware`**（docs.langchain.com，human-in-the-loop）

- 挂在 `create_agent` 的 `middleware` 里，`interrupt_on={"ask_user": {"allowed_decisions": ["respond"]}}`。模型发出 `ask_user` 调用时在**模型步之后、工具执行之前**中断，恢复时 `Command(resume={"decisions": [{"type": "respond", "message": 答案}]})`，答案直接作为该工具的结果回给模型。
- 同一轮里其他未配置的工具调用（如搜索）正常执行，不受中断影响。这正是 `ask_user` 需要的语义，第 10 节第 3 条"工具内 interrupt 会重放搜索"的顾虑因此不存在。
- 需要 checkpointer 和 `thread_id`，和现有 runner 一致。
- `langchain` 最新 1.4.7，依赖 `langgraph>=1.2.12,<1.3`，与现有 1.2.18 兼容。

**dev 上的 agent-tools 网关**（仓库 `~/code/agent-tools`，容器 `agent-tools-gateway`，2026-10-27 实测）

- 一个地址、一把产品密钥：`Authorization: Bearer <产品密钥>`，按前缀转发 `/search/...`、`/reader/...`、`/image/...`、`/trends/...`，网关记账（产品、用户、场景、请求 ID）。可选头 `X-Caller-User`、`X-Caller-Scene`、`X-Request-ID` 只用于统计。
- 搜索：`POST /search/search` `{"query","type":"web","count"}`，返回 `results[]{title,url,description,content(长摘要),published_at}`。dev 当前 provider 是 DeepSeek Search，可切 Brave / Tavily / Firecrawl；Redis 缓存。实测中文查询返回 5 条，带日期和长摘要。
- 读取：`GET /reader/read?url=...`，返回 Markdown 正文、标题、provider；直抓 1.5 s 未果并行走 Firecrawl / Tavily，Jina 兜底，总时限 10 s；失败给结构化 `kind`（page_not_found / timeout …）。实测 WorkBuddy 更新日志页直抓 1 s、5 万字。
- 这两个接口就是设计里 agent 的"搜索"和"抓取"工具，返回的就是候选列表和原文，不需要再包一层。
- 接入条件：网关 `PRODUCTS` 里加 `lingdraft`、`gateway/.env` 加 `LINGDRAFT_SERVICE_KEY`，重新部署网关；本机开发经 `agent-tools.dev.seanfield.org`（本机 curl 对其证书不信任，需确认）或 `ssh -L 8100:127.0.0.1:8100 dev` 隧道。

## 13. 实施记录 R1（2026-10-27）：豆包 function calling + create_agent 验证

脚本 `backend/scripts/probe_create_agent.py`（`PYTHONPATH=. uv run python scripts/probe_create_agent.py`），真实豆包 `doubao-seed-2-1-pro`，thinking 关闭，两个工具：假搜索、`ask_user`；`HumanInTheLoopMiddleware(interrupt_on={"ask_user": {"allowed_decisions": ["respond"]}})`，`InMemorySaver`。

三次运行都通过，流程一致：模型先调 `fake_search` → 再单独发 `ask_user`（带 question / options / why）→ 中间件在执行前中断，payload 为 `action_requests[].args` → `Command(resume={"decisions":[{"type":"respond","message":...}]})` 恢复 → 用户回答作为 `ask_user` 的工具结果回到模型 → 最终回答引用了搜索结果里的网址。`ask_user` 函数体从未被执行，符合预期。

| 段 | 耗时 |
|---|---|
| 首段（搜索 + 发起提问） | 6.8～9.3 s |
| 恢复后（收到答案 + 作答） | 5.1～7.6 s |

去掉"不要同一步调两个工具"的提示后，模型仍然串行调用，没有出现并行工具调用；并行场景下中间件的行为未验证，实现时保留该约束。

结论：豆包的 function calling 与 `create_agent`、HITL 中间件、checkpoint 恢复都兼容，`langchain` 1.4.7 已加入依赖。下一步接真实的网关搜索 / 读取工具。

## 17. 实施记录 R5（2026-10-28）：最小 B 流程 + 模型切换 DeepSeek V4 Pro

背景见 `调研场景问题梳理（供讨论）.md` §8～§11 与 `probe/autonomy/README.md`：按章调研 + 大纲卡的流程把"问题多深"固定成了"流程多重"，豆包在模糊题上 3/7 次无答案结束，DeepSeek V4 Pro 思考模式四例全部交付且最省。Sean 10-28 拍板：模型切 DeepSeek V4 Pro（思考 high），流程改成最薄的"全局 agent + 无工具结构化整理"。

### 流程

`intake → confirm_scope（只在 intake 提了问题时中断）→ research → consolidate →（有缺口回 research 一轮）→ write → check → review（中断）→ export`。

- `research`：一个全局 `create_agent`（搜索 / 读页 / `ask_user`），系统提示只给范围和额度，不规定章节；交付是**文字**（结论、事实 / 推断各带 URL、未定项），不再用结构化 `Answer` 工具。来源仍从工具消息收集进 state。
- `consolidate`：无工具的结构化整理（json_schema strict）：候选答案 + 已存来源 → 节、论断（带 ref 与 source_ids）、逐句挂论断、假设、`answered` / `gap`。代码校验 source_ids 必须在已存且未排除的来源里，无来源论断丢弃并记 note；推断句的「推断：」前缀由代码补，不靠模型。`answered=false` 且有 gap 时带着候选答案回 `research` 补一轮（最多 1 轮）。
- `write`：初稿直接拼装整理结果（不再过一次模型）；终审的排除来源 / 改论断 / 重写只重写受影响的节。
- `check`：加 `answer_present`——没有有效答案不算成功，受控收尾得到的答案标出来。
- 去掉：大纲卡、按章调研、`reopen_outline`、`Findings`/`ProposedClaim`。海报场景没动。

### 硬边界（代码层，不信模型自觉）

- `ToolBudgetMiddleware`：工具用够额度（搜 8 / 读 6 / 问 2）后从模型可见的工具列表里**摘掉**并在系统提示里说明，执行层再硬拦一次。针对探针里 DeepSeek 不思考模式无视错误连续调 22 次 read_page 的情况。
- `InvalidToolCallRetryMiddleware`：模型返回解析失败的工具调用（探针里的裸 ASCII 引号问题）时，把错误作为 ToolMessage 回给模型重发，最多 2 次，而不是像 `create_agent` 默认那样直接结束。
- `ModelCallLimitMiddleware(run_limit=30, exit_behavior="end")`；没有文字答案时 `close_out` 不带工具再请模型基于已有材料收尾（最多 2 次），仍没有就 `answer_how="none"`、报告为空但 note 与检查项写明，不假装成功。
- 整理与收尾各有独立重试次数；整理失败 note 记录、报告为空。

### 模型接入（`app/research_llm.py::make_chat_model`）

- DeepSeek 思考模式要把上一轮 `reasoning_content` 原样带回，`langchain-deepseek` 不做，子类 `_get_request_payload` 补；思考模式拒绝强制 `tool_choice`，去掉。
- 调研 agent：思考 high。结构化步骤（intake / 整理 / 重写）**不开思考**：思考模式整理一次 100～140 秒，比调研本身还慢；不思考 20～40 秒，json_schema strict 保证 JSON 合法，字段与引用由代码校验。
- `RESEARCH_PROVIDER` / `RESEARCH_MODEL` / `RESEARCH_THINKING` / `RESEARCH_EFFORT` 可切回豆包。

### 边界补洞（2026-10-28，Codex 离线复核后）

Codex 读代码并跑离线边界用例指出五个漏洞，核对后都成立，已修并各加测试（离线 57 个通过）：

1. **空报告能全绿导出**：整理失败时 0 节 0 论断，原有检查都是空集上的真空通过，`answer_present` 又只看整理前的候选答案。加 `report_valid`（至少一句挂着有来源的论断）和 `question_answered`（整理步骤的 `answered`）；`review` 的 approve 在 `report_valid` 未过时服务端拒绝，前端也不显示导出项。
2. **丢弃的无来源论断，句子仍留在正文**：原来把句子的 claim 关联置空，文字照样进报告。现在句子随论断一起移除并记 note；重写路径同样处理挂在不可用论断上的句子。
3. **额度能绕过**：同一批发 10 个搜索原来会执行 10 次（计数只看历史）；提问走 HITL 的 `respond` 在执行前返回，执行层拦不到。现在执行层按“历史 + 同批前序同名调用”计数；超额的 `ask_user` 在 `after_model` 里改名成 `ask_user_over_budget`（本中间件排在 HITL 之后、after_model 反序执行，所以先于 HITL 看到），HITL 不再把它变成问题卡，执行层回“额度已用完”。每轮的提问额度是整线程上限减去已问次数。
4. **受控收尾的历史不合法**：无效调用重试耗尽后，最后一条模型消息带着没有结果的工具调用，直接追加收尾要求会被 API 拒绝。收尾前给没有结果的调用（含 invalid_tool_calls）补错误结果。
5. **`answered=false` 且 `gap=null` 不回补**：现在以 `answered` 为准，没写 gap 就用默认缺口文字回补；补完仍没回答则 `question_answered` 不通过。

真实模型回归：天气题 22 秒、全过。

### 命名与流程
