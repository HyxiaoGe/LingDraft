# 调研交互约定：在 chat 上做 work（2026-10-30）

> **现状（2026-10-30 晚）**：调研这个方向先放下了，现在只做对话：能搜能读、回答里标来源、可以停止和重新回答。下面写的报告、论断、提问卡都已经从代码里拿掉，这份文档留作之后再做调研时的参考，不再是改代码前要对齐的约定。

这份文档记录 2026-10-30 讨论定下的方向和使用场景。动手改代码之前，先按这里对齐；使用场景同时是之后的验收用例。

标记说明：**已定** 是 Sean 拍板的；**待定** 是还没定、需要 Sean 决定的，有的附了 Claude 的建议，只作参考。

## 一、为什么要改

现在的调研是一条代码写死的单向流水线：

> 理解问题 →（有疑问时）问范围 → 调研 → 整理 → 写报告 → 校验 → 等确认

用户只能在三个固定的停靠点说话：开头问范围、调研中途模型提问、最后等确认。确认点上能改几轮，但只能在已查到的材料上改写，不能补查，也不能回头改范围。点了“不用改了”（或者用户的话被模型理解成确认），线程就结束了。

具体问题：

- **模型自己没说过话。** 调研完模型其实写了一段文字答案（state 里的 `answer`），但页面从来没显示，只拿去当整理的原料。中间栏的话是代码模板（“第 1 版报告在右边……”）。
- **chat 该有的东西都没有。**
  - 没有标题生成：侧边栏显示的是范围里的问题或原话；
  - 没有推荐问题；
  - 思考内容不给看：调研那一步开着思考，但没展示；
  - 状态都是代码写的标签；
  - 没有逐字流式；
  - 确认之后不能追问。
- **下一步做什么是代码定的。** 用户的话只能被理解成四种动作之一：确认、排除来源、改论断、重写一节。额度对所有问题都一样：每次调研最多搜 8 次、读 6 页，开头最多问 2 个问题，整条线程中途最多问 2 次，缺口最多补查 1 轮，原文只留 400 字。
- **证据偏薄。** 8000 上 20 条有报告的线程，报告引用了 270 条来源，读过原文的只有 35 条（13%），其余只有搜索摘要。10-30 的 954af53a 只搜了 3 次、一页没读，报告挂了 24 条来源。
- **评测只测了第一版。** 六个回放用例都是“问一个问题，出第一版报告”。出了报告以后接着说话的情况，一项都没测。

根子上的原因：先照 LangGraph 画了一条带审批点的固定流程；模型一出问题，就把那个判断收回给代码；拿“测试全绿、流程跑通”当验收；骨架不对的时候，还在上面打磨细节。

## 二、方向（已定）

1. **work 是在 chat 上加 HITL 和交付物，不是把 chat 换掉。** chat 原有的交互要保留，包括对话内容和后台的流式推送。
2. **每一轮都有正文回答。** 这一轮说的事和交付物有关，就同时更新交付物、出新一版，正文里说明这版改了什么。正文回答和交付物更新不冲突；更新不更新，由模型判断。
3. **正文是摘要和结论，报告是详细内容。**
4. **思考过程原样给，不加工、不摘要。** 边想边逐字推给页面，同时存下来，重新打开线程也能看到。
5. **不封版。** 去掉“不用改了”：第 1 版直接展示，输入框一直开着。想改就说，说了出第 2 版；不说，这版就是结果。模型理解用户的话时，也不再有“确认 / 结束”这个选项。
6. **下一步做什么，由模型判断。** 看了用户的话和当前报告，是只在对话里回答、更新报告、再去查，还是先问一句，交给模型。代码不写死路线。模型做得不好，改它的上下文和提示词，不把判断收回代码。
7. **chat 要素要补齐**（Sean 列的）：标题自动生成、正文结束后的推荐问题、思考过程的输出、正文的表达、agent 的各种状态。
8. **验收看能不能用它干活。** 下面的使用场景就是验收用例，要用真实模型跑多轮；测试通过只是底线。
9. **额度先不设，先放开，观察一段时间再说。** 去掉搜索、读页、提问、补查、模型调用的次数上限。每轮记下搜了几次、读了几页、用了多少 token，方便观察。代码守住三条：事实挂来源、不许编、交付前校验。花费上限先不设。
10. **开头的澄清统一成对话里提问。** 去掉单独的范围卡。模型觉得要问，就在对话里出提问卡，和调研中途提问是同一种卡。
11. **思考过程运行中展开，结束后折叠。** 一轮回复完成后折叠成一行“思考了 N 秒”，点开能看全文。一轮还在跑时，想完的那段也不收：收起来页面会往回缩、跳一下（2026-10-31 Sean 定）。
12. **不兼容旧线程。** 不为旧对话加兜底代码；旧线程影响实施的话直接删掉。

## 三、一轮回复长什么样

按顺序：

1. **工作过程**：原始思考，加上工具步骤（搜了什么、读了哪页、结果怎样），按发生的先后穿插排列。边跑边逐字出现。
2. **正文**：模型自己写的摘要和结论，带引用角标。逐字出现。
3. **交付物卡片**：只在这一轮新建或更新了报告时出现。写明“调研报告 · 第 N 版”和这版改了什么，点开在右栏看。
4. **推荐问题**：几条可以接着问的。正文写完这一轮就算结束（来源、时间、按钮马上出来），推荐问题晚一两秒再出；这期间用户说了话，这一轮的推荐问题就不要了，新的一轮马上开始，不排队（2026-10-31 Sean 定）。

标题在第一轮早期就生成，推送到侧边栏。

## 四、使用场景（验收用例）

每个场景写的是用户看到什么；“验收”写的是跑真实模型时要检查的点。

### 场景 1：第一次提一个需要调研的问题

用户：“DeepSeek V3 的训练成本到底是多少？不同说法差在哪？”

- 侧边栏很快出现一个生成的短标题。
- 对话里开始出现原始思考，接着是搜索、读页这些步骤，每一步有结果和状态。找到的来源边查边列，标明“读到原文 / 只读到摘要 / 没读成”。
- 思考和步骤结束后，正文逐字出现：结论是什么，几种说法分别从哪来、差在哪，带角标。
- 正文下面一张卡片“调研报告 · 第 1 版”，右栏出现报告全文。
- 最后几条推荐问题。
- 输入框一直可以用。

验收：

- 正文是摘要和结论，没有把报告整篇复述一遍；
- 正文和报告的结论一致；
- 思考是原样内容；
- 重新打开线程，看到的和刚才实时看到的一致：思考、步骤、正文、卡片、推荐问题都在，顺序不变。

### 场景 2：简单问题，不需要报告

用户：“新加坡现在是什么季节？”

- 有思考，必要时查一两下，然后直接给正文回答和推荐问题。
- 没有报告卡片，右栏不出现报告。

验收：

- 模型自己判断不需要交付物，没有为了走流程硬出一份报告；
- 之后用户说“整理成一份报告”，就出第 1 版。

### 场景 3：看完报告追问，不涉及改报告

用户：“为什么 SemiAnalysis 的估计比官方高这么多？”

- 正文直接回答，依据是已有的材料；需要的话，模型自己决定再查。
- 如果回答的内容不需要写进报告，就不出新版本。

验收：

- 是否出新版本由模型判断，而且判断合理；
- 不出新版本时，正文里不说“已更新报告”。

### 场景 4：要求补查

用户：“再查一下有没有第三方按 GPU 小时重新估算过。”

- 模型去搜、去读，过程照常显示。
- 正文说查到了什么、没查到什么。
- 报告出第 2 版，卡片上写明这版改了什么，比如“新增一段第三方估算”“第 2 节结论改为……”。

验收：

- 真的去查了，而不是在已有材料上改写；
- 第 2 版保留第 1 版里没被这次影响的内容；
- 改动说明和实际改动一致。

### 场景 5：改写某一段

用户在报告里选中一句，说“这里说得太绝对了”；或者在输入框说“第一节更简短”。

- 不需要查的就不查。
- 正文简短说明改了哪里，报告出新一版。

验收：

- 只改了用户指的地方，没把别处改坏；
- 改得到位（之前测过的问题是“没越界，但改得不够狠”）。

### 场景 6：排除一条来源

用户在角标的来源卡上点“排除”，或者说“第 3 条来源不靠谱，去掉”。

- 报告出新一版：只靠这条来源的说法去掉或改写，引用重新编号。
- 正文说明影响了哪些结论。

验收：

- 正文说的影响和报告里实际的变化一致。
- 排除以后怎么恢复，见待定第 9 条。

### 场景 7：什么都不说

- 第 1 版就是结果，不需要任何确认。侧边栏显示“第 1 版”，没有“等你确认”。
- 几天后重新打开，所有内容和当时一样，可以接着说，出第 2 版。

### 场景 8：模型中途需要问用户

调研中模型发现有歧义，比如“你要的是训练成本，还是含研发的总投入？”

- 对话里出现一张提问卡；用户回答或跳过后，模型接着查。

验收：

- 只在真的需要人决定时才问（沿用“问题卡只在需要人介入时出现”）；
- 问题和回答都留在对话里。

### 场景 9：额度用完或出错

- 额度用完：明确显示“搜索次数用完了，基于已有材料回答”这类原因，不悄悄收尾。
- 出错：显示原因和重试。已经拿到的内容不丢。

### 场景 10：刷新页面或断线

- 运行中刷新页面：重连后接着看到后面的内容，前面的不重复、不丢。
- 运行结束后，以存下来的状态为准，和实时看到的一致。

### 场景 11：运行中停止或插话（和待定第 1、7 条一起定）

- 停止：运行结束，原因写“用户停止”，已经查到的保留。
- 插话：比如“B 不用查了，查 D”，模型接着按新的意思做。

## 五、技术约定

### 事件和 state

- **state 是唯一的真相。** 来源、论断、版本、对话内容都存进检查点；重新打开线程按 state 画。
- **事件只是“刚刚变了什么”的实时通知。** 从 state 的变化和模型的逐字输出推出来，自己不保存数据。
- **事件里的内容最后都要落进 state。** 心跳、“正在想”这类纯提示的除外。现在 state 里没有“对话”这一层，模型的思考和正文只在 agent 子图自己的消息里。要补成“每一轮回复是一组有顺序的块”：思考、工具步骤、正文、交付物引用、提问卡、推荐问题。
- **事件和 state 用同一套 id。** 工具步骤已经用工具调用 id 对上实时和存档，新加的块照这个规矩来。
- **运行结束或重连后，以 state 为准重新对齐。**
- 已知边界：LangGraph 在步骤之间才存检查点。后台在一步中间挂掉时，页面上已经看到的部分逐字内容不会进 state，重新打开就没了。PoC 阶段可以接受。

### 事件（参考 Fusion，不照抄）

现在只有 8 种事件：`thread`、`started`、`progress`、`node`、`interrupt`、`state`、`error`、`end`。基本就是“哪一步做完了”加“整体快照”。

参考 Fusion 的形状：

- 两层：外层是逐字流和存活信号，里层是结构化事件；
- 统一信封：运行 id、步骤 id、工具调用 id、序号、时间；
- 消息按块存。

初步要有的事件（动手前再细化）：

- **逐字流**：思考片段、正文片段，都带块 id。
- **存活信号**：模型还没出字时的“正在想”、心跳。
- **运行生命周期**：开始、完成、失败、停止、到上限。完成要带原因（正常结束 / 到上限 / 没写完），停止要分“用户停止”和“被新请求顶掉”，到上限要说明是哪种上限。
- **工具步骤**：开始、完成，带成功 / 失败 / 降级、耗时、结果摘要。
- **来源（证据）状态**：候选 → 读到原文 / 只读到摘要 / 读失败 → 被正文用上 / 弃用，用上的带编号。
- **交付物**：新建或更新了第几版，带改动说明。
- **标题**：生成好就推。
- **推荐问题**。
- **每轮模型调用的 token 用量**：不一定给用户看，用来算一次调研花了多少钱。
- **计划**：见待定第 1 条。

Fusion 里现在不需要的：位置握手、模型切换、工具重试明细、系统提示词指纹、上下文裁剪。

### 逐字输出的验证（2026-10-30）

用 DeepSeek V4 Pro（思考 high）实测，脚本没进仓库：

- **直接流式**：先逐字推思考（0.9 秒出第一个字），思考完再推正文（3 秒）。先后清楚，不混在一起。
- **照调研节点的方式跑**：LangGraph 节点里用 `build_agent` 建的 agent 一次性调用，中间带一次工具调用，外层用 `stream_mode="messages"`、`subgraphs=True`。顺序是：思考 → 生成工具调用 → 工具结果 → 再思考 → 正文。每一片带所属节点和子图。
- **不用改节点里的调用方式**，外层就能逐字拿到。
- **逐字输出后，思考内容会拼回完整消息**，带工具调用的第二轮能原样传回，DeepSeek 没报错。

还没验证：

- 后端现在只订阅了 `updates`、`custom`，要加 `messages`；
- 整理、写报告用的快模型走结构化输出，那些 JSON 片段也会被推出来，要按节点过滤；
- `ask_user` 打断和逐字输出同时出现的情况；
- 豆包那条路用 `ChatOpenAI`，会丢掉思考内容。

## 八、第一批怎么做（实施设计，2026-10-30）

范围：场景 1 到 10。计划、停止、插话、重新生成、会话管理、版本对比、恢复排除的来源放到第二批。

### 骨架

- **一条线程就是一个 agent 的对话。** 不再有“理解问题 → 问范围 → 调研 → 整理 → 写报告 → 校验 → 等确认”这条外层流程。线程的图就是 `create_agent` 建的那个 agent，检查点挂在它上面；消息列表就是对话记录，每说一句话就接着跑一轮。
- **一轮里做什么，由模型自己用工具决定。** 工具有八个：
  - 查资料：`search_web`、`read_page`、`load_skill`；
  - 问用户：`ask_user`，开头澄清和中途提问都用它；
  - 改交付物：`write_report`、`revise_section`、`edit_claim`、`exclude_source`。
  不调工具时写出的文字就是这一轮的正文。不需要报告的问题，就不调改报告的工具。
- **报告还是“整理成节、论断、来源 → 拼装 → 校验”。** 区别有三点：
  - 草稿由 agent 写，写在 `write_report` 或 `revise_section` 的参数里；
  - 整理（快模型）把草稿拆成节和论断，挂上来源；
  - 每个改报告的工具都把改完的整份报告原样返回给 agent，agent 始终知道报告现在是什么样。
- **一轮最多出一版。** 这一轮里改报告的工具都只改“工作稿”，每次调用写一句改动说明。这一轮结束时，有改动就落成第 N 版（写文件、跑校验），改动说明拼成版本说明。
- **来源 id 在工具结果里给出。** 搜索和读页结果里，每个网址带一个由网址算出来的短 id（`s` 加 6 位十六进制）。
  - 同一个网址永远是同一个 id；
  - 正文和草稿用 `[s3fa9c1]` 引用；
  - 页面上，正文和报告各自按出现先后编 1、2、3。
- **标题和推荐问题。** 第一轮开始前，快模型起一个短标题；每轮结束后，快模型给 3 条推荐问题。都存在 state 里。
- **每轮的记录**（`turns`）：开始和结束时间、出了第几版、推荐问题、用量（模型调用次数、输入和输出 token、搜索和读页次数）。
- **思考。**
  - 思考内容就是模型返回的 `reasoning_content`，原样存在消息里；
  - 只把这一轮的思考传回 DeepSeek，前几轮的不传；
  - 思考了几秒，由模型调用时的回调记下来，也存在消息里。
- **不设上限。** 去掉 `MAX_*` 这些额度和调用上限。LangGraph 自带的递归上限默认是 10007 步，相当于不限。

### 事件

- `delta`：思考片段和正文片段，带消息 id；
- `step`：工具开始和做完，带工具调用 id；
- `writing`：正在写报告草稿，带已写的字数；
- `title`：标题；
- `node`：存下了一步，页面据此重新取一次状态；
- 另外保留 `thread`、`started`、`interrupt`、`state`、`error`、`end`。

消息 id 和工具调用 id 跟 state 里的一致。页面按 state 画已经存下的部分，没存下的部分用事件叠上去。

### 接口

- 新建：`POST /api/research/threads {text}`；
- 接着说：`POST /api/research/threads/{id}/messages {text, quote?, action?}`。
  - 报告上的按钮（排除来源、改表述、重写这一节）和选中文字后说的话，都走这个接口，作为用户的一句话交给 agent；
  - `action`、`quote` 里带着对象 id。
- 回答提问卡、重试、接上事件流、取状态：和现在一样。
