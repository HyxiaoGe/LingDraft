## middleware 的钩子按什么顺序跑

一共六种钩子：

- 整轮一次：before_agent、after_agent；
- 每次调模型前后：before_model、after_model；
- 包住一次调用：wrap_model_call、wrap_tool_call。

`create_agent` 是这样串起来的（`factory.py` 加边的那一段）：

- before_agent、before_model：按 middleware 列表的顺序跑。
- after_model、after_agent：倒过来跑，列表里最后一个先跑。
- wrap_model_call、wrap_tool_call：列表里第一个包在最外层，最后一个离模型和工具最近。

实验 `order`：在我们的 4 个前后各插一个只打日志的 A 和 Z，跑一轮"搜 → 读 → 答"，顺序和上面一样：

- A.before_agent → 我们的两个 before_agent → Z.before_agent；
- 每次调模型：A.before_model → Z.before_model → A.wrap 进 → Z.wrap 进 → 模型 → Z.wrap 出 → A.wrap 出；
- 接着 Z.after_model → 我们的 after_model → A.after_model；
- 每次调工具：A.wrap_tool_call 进 → Z 进 → 工具 → Z 出 → A 出；
- 最后 Z.after_agent → 我们的 after_agent → A.after_agent。

另外两点：

- **每个 before/after 钩子都是图里单独的一个节点，算一步，也就是一个检查点。** wrap 的两种不是节点，跑在 model、tools 节点里面。我们一轮"搜、读、答"是 11 步：2 个 before_agent，3 次"模型 + after_model"，2 次工具，1 个 after_agent。这就是第二篇里一轮 11、12 个检查点的来历。
- 一次回复里有几个工具调用时，`model` 到 `tools` 的那条边是每个调用发一个 `Send("tools", [这个调用])`，它们并行跑（`_make_model_to_tools_edge`）。`Send` 放到第 5 篇细看。

对照我们挂的 4 个：

- TurnMiddleware：before_agent 记下这一轮从哪句话开始、第一轮起标题；wrap_model_call 换系统提示词、接时间说明；after_agent 收尾这一轮。
- ContentGuard：wrap_model_call 去掉被拦停过的轮次，被审核拦下时去掉没过审的资料再试。它在 TurnMiddleware 里面一层，所以再试的请求也带着换好的系统提示词和时间说明。
- ToolProgressMiddleware：wrap_tool_call 推进度。
- InvalidToolCallRetryMiddleware：before_agent 清计数，after_model 遇到只有无效工具调用时补上错误结果，跳回模型重发。

## SummarizationMiddleware 怎么工作

**什么时候压**

- 挂在 before_model 上，每次调模型前判断一次。
- `trigger` 可以按 token 数、消息条数、占模型上限的比例来设，可以组合。**默认不设，也就永远不压。**
- 按比例要模型的 profile 里有上限。DeepSeek V4 Pro 的 profile 写的是输入 100 万 token。

**token 怎么数**

- 默认按 4 个字符算 1 个 token 估算。
- 再用最后一条模型消息报的用量校正，但最多放大到 1.25 倍。
- 用真实数据比了一下：我们的对话里，模型报的输入 ≈ 4 千（系统提示词和工具说明）+ 1.68 × 估算。中文按 4 个字符一个 token 太少了，校正也补不回来。
- 触发那一侧还有一条路：最后一条模型消息的提供方和压缩用的模型对得上时，也拿它报的用量判断，估算和报的用量哪个过了线都触发。我们的消息标的是 `deepseek`，`ChatDeepSeek` 也是 `deepseek`，这条路走得通。
- 但报的是**上一次调模型**的用量（`_should_summarize_based_on_reported_tokens` 读最后一条 AI 消息的 `total_tokens`），那之后加进来的工具结果不算在内，所以会晚一步：比如刚读了一个很长的网页，这次请求实际已经过线了，估算又偏少，就照常发出去，要到下一次才压。（11-02 改，原来写的是"按 token 触发是准的"）
- 不准的是"留多少"那一侧：`keep` 按 token 算时只能用估算，实际留下的会比设的多 70% 左右。

**压哪些**

- 留最近的 `keep`（默认 20 条消息），前面的压掉。
- 切的位置不会把模型的工具调用和它的结果分开，碰上了就往前挪。

**摘要怎么写**

- 默认提示词是英文的，分四节：用户意图、要点、用到的资料、下一步。
- 写摘要的模型默认就是被压缩的那个模型，可以另指一个，也可以传一个函数。失败了重试，最多 3 次。
- **只送要压掉的那部分的最后 4000 token**（`trim_tokens_to_summarize`），而且要从一条用户消息开始。更早的内容不进摘要，直接没了。
- 取出来是空的时候，摘要就是一句固定的话 "Previous conversation was too long to summarize."，不调模型。

**怎么写回状态**

- 返回 `RemoveMessage(REMOVE_ALL_MESSAGES)`，加一条摘要，再加留下来的消息。状态里的消息就被整个换掉了。
- 摘要是一条用户消息（HumanMessage），开头是 "Here is a summary of the conversation to date"，标了 `lc_source: summarization`。
- 旧消息只在更早的检查点里还有，时间回溯能找回来，当前状态里没有了。

写摘要那次模型调用带了内部标记，LangGraph 新的流式接口（`run.messages`）靠 `InternalCallTransformer` 把它滤掉。我们的运行器只转发 `langgraph_node == "model"` 的片段，摘要是在 before_model 节点里调的，本来就不会混进正文流，实验里也确认了。

## 挂到灵稿上会怎样（实验）

**baseline**（不压，连说 4 轮）：状态 24 条消息，页面 4 轮，来源 12 条。

**summarize**（消息到 14 条就压，留最近 6 条）：

- 4 轮里压了两次。
- 状态最后剩 8 条：摘要、上一轮的半截、最后一轮。
- 页面只剩 2 轮。第一轮显示成"用户说：Here is a summary of the…"，没有这一轮的记录；前 3 轮都不见了。
- 来源从 12 条剩 3 条，前面回答里的引用编号都对不上了。
- 原因：页面上的轮次、过程、来源，都是从状态里的消息算出来的（`conversation`、`collect_sources`）。状态既是给模型看的上下文，也是给人看的记录，压缩把两样一起删了。

**summarize-cut**（留得很少，一轮里就压，这一轮用户的话也被压掉了）：

- 模型看到的"用户的话"成了那条摘要。
- 它看不到自己已经搜过（搜过的次数从 1 变回 0），又搜了一遍。
- 这一轮的记录丢了：记录是按用户那句话的 id 挂的，那条消息没了。
- 第一次跑这个实验，一轮压了 2500 次：留下的消息里没有搜索那一步，假模型就再搜，消息一多又压，压完又搜。后来改成只压一次。真模型会看摘要，不一定绕圈，但这一轮做到哪儿确实丢了。

**真实数据**（最长的那个对话，25 条消息）：

- 按默认留 20 条压一次，要压掉 5 条，约 5 千 token。
- 按留 6 条压一次，要压掉 19 条，约 1.65 万 token，里面有 4 句用户的话。
- 两种情况下，送去写摘要的都是 0 条。原因是一页读下来的正文就超过 4000 token，末尾 4000 token 里没有用户消息。最后写进去的摘要就是那句 "Previous conversation was too long to summarize."。**按默认参数用在我们的对话上，压掉的内容全丢。**

**踩到的一个坑**：压缩实验第一次跑就卡死了。原因是我们的假模型给消息编 id 用的是"消息条数"。压缩以后消息变少，新 id 和留下来的旧消息撞上，`add_messages` 按 id 替换那条旧的，不追加到末尾。路由找的是列表里最后一条模型消息，现在是一条工具都已经有结果的旧消息，于是又转回模型（`_make_model_to_tools_edge` 第 6 条）。消息条数没变，下一次的 id 还是撞，就一直绕。真模型的 id 是随机的，不会这样；实验里给假模型加了随机后缀。要是以后用假模型测压缩，测试里也得这么做。

## ContextEditingMiddleware：只改发给模型的那一份

`context_editing.py`，照的是 Anthropic 的 context editing。

**机制**

- 挂在 wrap_model_call 上，复制一份这次要发的消息再改，**状态不动**。
- 默认估算超过 10 万 token 时，把较早的工具结果换成 `[cleared]`，留最近 3 个。
- 可以连工具调用的参数一起清（`clear_tool_inputs`），可以排除某些工具（`exclude_tools`），可以设一次至少清掉多少（`clear_at_least`）。

我们原来的 `with_time_note` 也是这个做法：几点钟只接在发给模型的那一份上，存下来的消息不带（2026-11-01 改成了取时间的工具，见下面）。

**实验 context-edit**（超过 3000 token 就清，留最近 2 个）：

- 状态 24 条消息原样，页面 4 轮、来源 12 条都在。
- 发给模型的，从第 6 次调用起有 2 到 6 个工具结果被换掉。
- 发出去的 token 从约 4.1 万降到约 2.1 万。

## 真实对话有多长、钱花在哪

**有多长**

- 17 个对话里，单次调模型的输入最大是 4.5 万 token，不到 DeepSeek V4 Pro 上限的 5%。
- 消息里 85% 到 95% 是工具结果，主要是读页正文。

**钱花在哪**

- DeepSeek V4 Pro 的价格（官网价格页，闲时）：输入命中缓存 0.15 元/百万 token，没命中 4.5 元/百万 token，差 30 倍；输出 13.5 元/百万 token。高峰时段都翻倍。
- 17 个对话一共输入约 82 万 token，命中缓存 61%。按上面的价格，命中的那部分只占输入花费的 5% 左右，花钱的是没命中的那 39%。
- 所以压缩省下的主要是本来就命中缓存、几乎不要钱的那部分。如果压缩让开头变了、命中率掉了，反而更贵。

实验里按"开头和之前某次调用一样的能命中"估了一下。没命中的分两种：一种是之前发过、但开头对不上了；一种是第一次发、本来就省不了。4 轮下来：

- 不压：没命中的约 1.25 万 token，其中 0.54 万是开头对不上的。
- 摘要：发得少了，但没命中的约 1.45 万，还没算写摘要那两次调用。
- 清工具结果：发得只有一半，但没命中的约 1.69 万。清掉的位置每次在变，开头总是对不上。

把命中折成未命中的 1/30，输入花费大致是：摘要比不压贵 11%，清工具结果贵 27%。这是估算：DeepSeek 实际按 64 token 一块算缓存，假数据的比例也和真实对话不完全一样。

### 顺带发现：每轮第一次调用丢了上一轮的缓存

先说结论，有两处原因，都在我们自己的代码里，断的位置只差几十个 token：

- `with_time_note` 只把几点钟接在最新一条用户消息后面。到了下一轮，上一轮那条用户消息发出去时就不带时间了，开头从那里起对不上。
- 发给 DeepSeek 时，只把这一轮的思考（`reasoning_content`）传回去，之前几轮的不传（`research_llm.make_chat_model`）。到了下一轮，上一轮的模型消息少了思考，和当时发出去的不一样，开头紧接着上一轮那句话之后也对不上。

一开始只看到了第一处。2026-11-01 把几点钟改成工具以后跑真实模型，第二轮还是只命中到上一轮那句话，才查出第二处，见本节最后。

真实数据（最长的那个对话）里，每一轮第一次调用命中的缓存，都正好约等于上一轮第一次调用的输入：

- 第 3 轮命中 13440，第 2 轮第一次输入 13490；
- 第 4 轮命中 20480，第 3 轮第一次输入 20516；
- 第 5 轮命中 29824，第 4 轮第一次输入 29904。

也就是说，缓存只命中到上一轮那条用户消息，上一轮的搜索、读页结果在新一轮里都按没命中的价格再算一遍：

- 这个对话 5 轮，这样多算的至少 3.4 万 token。
- 17 个对话一共没命中 32 万 token。其中每轮第一次调用没命中 9.9 万，按"上一轮最后一次调用的输入本该能命中"算，有 9.1 万到 9.6 万是这样多算的，占全部没命中的 28% 到 30%。
- 剩下的 22 万是一轮里新读到的正文，省不了。
- 折成钱不多：17 个对话的输入一共约 1.5 元（闲时价），多算的约 0.4 元。比例是近三成。

第一处是照 Fusion 写的（`with_time_note` 的注释："照 Fusion：几点钟只接在最新一条用户消息后面"）。本意是不让时间进系统提示词，免得前缀每分钟都变。它确实做到了这一点，但每轮会丢上一轮的缓存。

第二处的理由写在测试里："传了接口也不用，白占上下文"。DeepSeek 的思考模式文档对不带工具的请求是这么说的；对带工具的请求（我们每次都带）写的是：历史轮次的思考都应该传回，而且会拼进上下文。

2026-11-01 的验证（`evals` 的 time-of-day 用例，两轮，结果里的 `calls`）：

- 只改了时间：第二轮第一次调用输入 9058，命中 5888，只到第一轮那句话为止。
- 再临时改成之前几轮的思考也传回：第二轮第一次调用输入 8049，命中 7936，整个第一轮都接上了。

两处都改才接得上，只改一处没用。上面估的"没命中的少近三成"要两处都改才拿得到。

## 建议（等 Sean 定）

1. **现在不加压缩。**
   - 离上限还远（最长的不到 5%）。
   - 按上面的估算，在我们这里两种压缩都更贵：命中缓存的部分几乎不要钱，压缩只会让命中率掉下来。
   - SummarizationMiddleware 还有两个问题：一是会改写状态，页面上的旧轮次、来源、记录都会丢；二是按默认参数，在我们的数据上写不出摘要。
2. **以后真要压**（比如长对话接近上限）：
   - 照 ContextEditing 的做法，只改发给模型的那一份，状态不动，页面照常；
   - 触发点设得高，比如几十万 token，但要给模型上限留出一次工具结果的余量（触发会晚一步，见上面"token 怎么数"）；
   - 一次清一大段（`clear_at_least`），不要每次清一点，让开头尽量少变；
   - 要写摘要的话，摘要存进状态里单独一个字段，消息不删，发给模型时再拿摘要替换掉前面那段；`trim_tokens_to_summarize` 设成 None，或者设得够大。
3. **每轮丢上一轮的缓存**：时间说明可以改成每条用户消息都带它自己那一轮开始的时间。这样已经发过的内容不会变，前缀就稳定了，按真实数据估计，没命中的能少近三成（17 个对话约 0.4 元）。代价是模型能看到每句话是几点问的，和 Fusion 的做法不一样了；这改的是给模型看的内容，要不要改由 Sean 定。

   2026-11-01 Sean 定：不往消息里放时间，改成加一个取当前时间的工具 `get_current_time`，问题跟几点有关时模型自己调。

   另一处 Sean 也定了改：之前几轮的思考也传回 DeepSeek，照它现在的文档。只传正文是这几年的主流做法（OpenAI GPT-5.6 之前、Claude Sonnet 4.5 及更早），新一代在改成保留之前几轮的思考（Claude Opus 4.5 和 4.6 以后、OpenAI GPT-5.6 默认、DeepSeek V4 带工具时）。两处都改了，发给模型的开头每轮都接得上。

## 2026-11-03：做进产品

Sean 定的：

- 两层都做。发给模型的估算超过 20 万 token 时触发，压到 10 万左右。两个数是环境变量 `COMPACT_TRIGGER_TOKENS`、`COMPACT_TARGET_TOKENS`。
- 之前几轮的思考清掉。
- 页面上不提示。
- 第二层用户的话照原样留着，只压模型那边。
- 取回工具 `recall` 两种都做：按来源 id、按轮。页面上不显示。

代码在 `backend/app/graph/research/compaction.py`。

**怎么做的**

- 只改发给模型的那一份，state 里的消息不动，页面照常。思路照上面的 ContextEditing，但两个 LangChain 的 middleware 都没用：
  - ContextEditing 每次调模型都现算从哪儿清，缓存每次都断；清掉的只剩 "[cleared]"，没有来源 id。
  - Summarization 会改写 state。
- 压到哪一轮记在 state 的 `compaction` 字段里，只往后挪。边界没挪的时候，每次拼出来的都一样，缓存接得上；只在挪的那一次断一次。所以一次压一大段（压到触发线的一半左右）。
- 每次调模型之前估一下：系统提示词、工具定义、消息都算。照 DeepSeek 文档的换算，英文字符约 0.3 个 token，中文约 0.6 个。超了就压：
  - **第一层**：从最早的一轮起，搜索、读页、取回的结果换成一行说明（来源 id、标题、网址，要原文就调 recall），思考不带。工具调用本身、子任务的报告、天气、画图的结果都留着。压到目标以下就停。
  - **第二层**：第一层压完还超，再从最早的一轮起，把模型那边换成 Flash 写的短版。短版一轮一份，写一次存进 state，以后不改。用户的话照原样。特别长的用户消息（超过 2 万字，比如贴了一大段）也换成短的，这条是我定的。
  - 这一轮（还在跑的）不压。
- 短版写失败了，那一轮先按第一层发，下次超了再写。写的时候用户点了停止，照常停。
- `recall`：
  - 按来源 id，给那个来源当初拿到的样子：读过的给读页的结果，没读过的给搜索结果里那一条。子 agent 查到的也算。
  - 按轮，给那一轮用户的原话和模型最后的回答。
  - 被内容审核停下的那几轮取不回：发给模型又会被拦。
  - 工具一直挂着：工具列表一变，缓存整个断。
- 缓存断了记警告：命中的不到上一次输入的一半，日志里记"前缀缓存没接上"。边界刚挪的那次不记。

**真实模型验证**

主 agent 用 DeepSeek V4 Pro，短版用 Flash。触发线调低到一两万，几轮就过线。脚本是 `实验/03-summarization/real_run.py`。

- **两条用户消息挨着**：换成短版的那一轮里，如果用户中途插过话，发出去就是两条用户消息挨着，后面才是模型的短版。单独发了一次，DeepSeek 接受。
- **第一层**：
  - 第 1 轮读 Python 3.14 的 What's New，第 2 轮问 Rust 2024。
  - 第 3 轮问"第一轮读的官方文档里，自由线程那段原文怎么说"。
  - 模型调了 recall 取回那一页。当初读到的那页本来就被截断了，自由线程那段不在里面，模型如实说了，没编。recall 取回的东西是对的。
- **缓存**：过线那次只命中系统提示词和工具（6912）。之后接上了：
  - 第 2 轮第二次输入 13624，命中 8320；第三次输入 14102，命中 13824；
  - 第 3 轮第一次输入 15393，命中 15232。
- **第二层**：
  - 第 2、3 轮开始时，之前的轮都换成了短版。
  - 第 3 轮问"第一轮回答里列的第二个新特性是什么，来源是哪篇"。模型只靠短版就答对了：注解延迟求值（PEP 649/749），来源 [s949b8a]。
  - 短版里留着来源 id。
  - 第 3 轮第一次输入 8204，命中 7552。第一轮的短版没变，缓存接到了它后面。
- **估算**：比实际多两三成（估 9539，实际 7558），多出来的主要在工具定义上。在 20 万的线上只差几千 token，早压一点没关系，没去校准。
- **花费**：两次主 agent 约 0.35 元（闲时价），Flash 写短版几分钱。

**没验证的**

- 真到 20 万的长对话没跑过。现在最长的对话才 4.5 万，专门造一个太贵。
- 特别长的用户消息换成短的，只用假模型测过。
- 子 agent 不压：有搜索、读页的预算，长不到这里。
- 页面没专门看。压缩不改 state，页面照常从 state 取；recall 不在页面的步骤里，这两点测试里看过。
