# 面试笔记：子 agent 过度调用工具，怎么发现、怎么解决

2026-11-02 整理。详细过程和全部数字见 [06-子agent查个没完.md](06-子agent查个没完.md)。

## 一句话版本

多 agent 调研里，子 agent 不管任务大小都把工具调用用到头。先用实验证明改提示词管不住，再调研业界做法，用对照实验选出"每步告诉模型还剩几次"这一招，配上 LangChain 的按工具硬上限接进产品。跑飞的情况从 4 分多钟降到 3 分钟以内，花费减半。

## 背景

- **系统**：灵稿的对话 agent，基于 LangChain `create_agent`（底层是 LangGraph）。
- **分工**：主 agent 用 DeepSeek V4 Pro，遇到要查很多资料的问题，用 `task` 工具派几个子 agent 并行去查。子 agent 用更便宜的 deepseek-flash，在自己的上下文里搜索、读网页，最后交回一份报告，主 agent 汇总后回答用户。
- **原有限制**：每个子 agent 最多调 12 次模型，最后一次关掉工具、让它用已有材料写报告。

## 问题

- **现象**：子 agent 不管任务难易，都把 12 次调用用到头或接近用完。
  - 一次三城购房政策对比，每个子 agent 搜了 24～31 次，这一轮跑了 257 秒。
  - 用户的感受就是慢，也费钱。
- **难点**：提示词里本来就写了预算（照 Anthropic 研究子 agent 的写法：简单任务 5 次以内、很难的最多 15 次）。模型会先给自己定一个预算，查着查着说"预算还够"，一直用到上限。
- **另一个容易漏掉的点**：模型一次回复能并行发好几个搜索。三城那次每个子 agent 只调了 8～9 次模型，搜索却有 80 次。只限调模型的次数，限不住工具调用。

## 解决过程

### 1. 先试最便宜的：改提示词

- 试了两种写法：按工具调用次数写、按"轮"写。都管不住，Flash 照样用到上限。
- **结论**：光靠提示词不行，得换思路。不再反复调措辞。

### 2. 调研业界怎么做

读了十来家的源码或原文：Anthropic 的工程博客和公开提示词、LangChain 的 open_deep_research、deepagents 和限制 middleware、OpenAI Agents SDK、smolagents、Google ADK、Jina DeepResearch、GPT Researcher，还有几篇论文。

- **共同点**：所有框架都靠代码硬上限兜底，提示词里的预算都是软的。
- **到了上限怎么收尾，分三种**：
  - 直接报错或停下，不给答案：OpenAI Agents SDK、Google ADK、LangChain 的限制 middleware；
  - 再调一次不带工具的模型写答案：smolagents、open_deep_research、Jina；
  - 根本没有循环，查几轮由代码定死：GPT Researcher。
- **最有用的线索**：Google 的 BATS 论文（arXiv 2511.17006）。每次工具结果回来，紧跟着告诉模型每种工具"用了几次、还剩几次"。

### 3. 对照实验：选哪种做法

- **怎么比**：拿两次真实运行里主 agent 写好的 6 份子任务当固定输入，直接跑子 agent，每种做法拿到的任务一模一样。
- **比了 5 种**：
  - 现在的提示词；
  - 换成 open_deep_research 的写法；
  - 调用上限从 12 降到 6；
  - open_deep_research 的写法，再把读页也算进预算；
  - 再加上每步预算提醒。
- **结果**：
  - 换 open_deep_research 的写法：搜索少了，但省下来的换成了读网页，有一个读了 16 页。
  - 上限降到 6：每个都撞上限，而且因为一次并行搜好几个，搜索还有 74 次。
  - 把读页也写进预算：还是有两个各搜了 9 次。
  - **只有加了每步预算提醒的那种，6 个子 agent 每个都正好守住预算**：搜索从 107 次降到 30 次，花费降 53%，用时减半。
- **代价**：让 Flash 当评委成对比较报告，几乎每份都判原来的更全，缺的多是细节，比如补丁修了什么、某个区的补贴金额。质量大致跟查的总次数一起走，没有能少查又不丢东西的写法。

### 4. 接进产品

- **硬上限，用 LangChain 现成的 `ToolCallLimitMiddleware`**（continue 模式）：
  - 搜索、读页各挂一个实例。
  - 超了的调用不执行，模型收到一句"不要再调这个工具"，然后自己决定接下来做什么。同一批并行调用里没超的照常执行，只拦超出的。
  - 次数存在 agent 的状态里，跟着检查点存，出错重试时接着算，不会清零。
- **没用 `ModelCallLimitMiddleware`**：到上限后它塞一句话就结束，模型没机会写报告。原来"最后一次关掉工具写报告"的做法保留。
- **每步预算提醒，自己写的，十来行**：在 `wrap_model_call` 里，工具结果回来后，请求末尾加一条 `<budget>` 消息，次数直接读上面那个组件记的。这条只在请求里，不存进对话记录。
- **体验细节**：被拦下的调用不在页面上显示，也不算进用量。顺手修了一个老 bug：参数解析失败、没真执行的调用，以前会被算进搜索次数。
- **测试**：用假模型写了"不管预算一直并行搜"的场景，验证被拦、提醒的数字、重试后次数接着算。

### 5. 端到端验证

- **设置**：主 agent 用 Pro，两个问题，比较三种：不设预算、每个子 agent 搜 5 读 5、搜 8 读 8。
- **结果**：
  - 预算每次都守住了。
  - 主要作用是收住跑飞的情况：三城那题用时 257 秒降到 154～176 秒，花费减半。没跑飞的那题，花费和用时差别不大，端到端的时间主要花在主 agent 写回答上。
  - 少查的细节对最终回答影响多大，这次没测准（见下面"没解决的"）。
- **决定**：每个子 agent 固定搜 8 次、读 8 页。不让主 agent 按任务动态给预算，多一个环节就多一个出错的地方，先固定，看数据再说。

## 可以讲的知识点

1. **提示词约束是软的，代码约束是硬的。** 用户体验和成本相关的上限，一定要有代码兜底。提示词负责让模型"愿意"省着用，代码负责"保证"超不了。
2. **说明放在哪里很关键。** 同样的预算信息：放在系统提示词里，模型会忘；放在请求最末尾，模型就守住了。之前还遇到过同类 bug：最后一步"写报告"的说明放在系统提示词里，上下文一长，Flash 没注意到，还想调工具，工具又关了，就把工具调用的原始标记当正文写了出来。挪到请求末尾就好了。
3. **限调模型次数 ≠ 限工具调用。** 模型支持并行工具调用以后，一次回复可以发好几个调用，所以要按工具分别限。
4. **到上限后要给模型一次收尾的机会。** 直接报错停掉，用户什么都拿不到。最后一次关掉工具让它写报告，用户至少拿到一份有来源的结果。
5. **评测本身要可信。**
   - 输入固定，只变要比的那一项。
   - 成对比较时交换前后位置，抵消评委的位置偏好。
   - 同一版本重跑一次，量出评委加上运行本身的波动有多大。
   - 这次就发现了评委偏向长回答：6 次比较全是长的那份赢，所以那一层的结论不能信。
6. **成本和质量的取舍是产品决定，不是技术问题。** 查得少，细节就少。技术上能做到的，是把"查多少"变成一个真能调的旋钮，让产品按需要定数。
7. **借助框架，不重造轮子。** 硬上限用 LangChain 现成的，自己只补框架没有的那一块（提醒），并处理它和产品其他部分的衔接（页面显示、用量统计、检查点）。

## 两分钟讲法

> 我在做一个多 agent 调研功能：主 agent 把问题拆开，派几个子 agent 并行去搜、去读，最后汇总。上线测的时候发现，子 agent 不管任务难易都把调用次数用满，有一次一个子任务搜了 31 次，一轮要 4 分多钟。
>
> 我先试了改提示词，照 Anthropic 和 LangChain 公开的写法写预算，都不管用：模型会说"预算还够"，一直用到上限。所以我去看了十来家框架和几篇论文，发现大家都靠代码硬上限兜底，Google 有篇论文提出每一步告诉模型还剩多少预算。
>
> 我用固定输入对比了 5 种做法，只有加了每步提醒的那种，每个子 agent 都守住了预算，成本降了一半。另外还发现，模型会并行发好几个搜索，只限调模型次数限不住，要按工具分别限。
>
> 接进产品时，硬上限用的是 LangChain 现成的 middleware，提醒那一段是我自己写的，放在请求最末尾。端到端看，跑飞的那种情况从 4 分多钟降到 3 分钟以内，花费减半。代价是细节会少一些，所以预算定多少是产品取舍，我们定了每个子 agent 搜 8 次、读 8 页。

## 可能被追问的

- **为什么不直接把调用上限调小？**
  试过从 12 降到 6：每个子 agent 都撞上限，细节也少了。而且模型一次能并行搜好几个，搜索还有 74 次，没限住真正花钱的地方。

- **为什么提示词管不住？**
  观察到的现象：模型会先定个预算，然后每一步都觉得"还够"。按工具调用次数写的时候，它数的其实是自己回了几次，不是调了几次工具；告诉它上限是多少，它就照着上限用满；改成按"轮"写，也一样用到头。根本原因说不准，但结论很清楚：只靠提示词不可靠。

- **为什么放在请求末尾就管用？**
  经验上，长上下文里模型更注意最近的内容。系统提示词在最前面，十几轮工具结果之后就被冲淡了。末尾那条每步都更新，模型做决定时正好看到。"最后一步写报告"那个 bug 也是同一个原因，改法也一样。

- **你怎么知道质量没降？**
  子 agent 那一层测到了，确实少了细节。最终回答那一层没测准：同一版重跑一次，评委打分的波动就一样大，而且评委偏向长回答。要测准，我会先列一张这道题该有的事实清单，逐条对照，每种做法多跑几次。

- **评测是怎么做的？**
  见上面"知识点 5"。补充一个数：整个调研和实验花了大约 1.3 美元。开跑前先估成本，并发不超过 3，跑的过程中盯搜索服务的额度，不让它自动转到付费的备用服务。

- **并行调用超预算时怎么处理？**
  LangChain 那个组件按顺序给同一批调用计数：没超的执行，超出的那几个回一条错误结果，模型下一步就知道了。

- **出错重试，次数会不会清零？**
  不会。次数存在 agent 的状态里，跟着检查点走，重试从检查点接着跑，次数也接着算。有测试覆盖。

- **和 BATS 论文有什么不同？**
  论文要解决的问题正好相反：它的模型是预算给多了用不完、提前收工。同一个办法两头都管用，因为它解决的是"模型看不见自己还剩多少"。

- **为什么不让主 agent 按任务动态给预算？**
  多一个让模型做判断的环节，就多一个出错的地方。先用固定值，有数据说明不够再说。

- **还有什么没解决的？**
  - 最终回答的质量影响没测准，原因见上。
  - 主 agent 派不派子 agent 本身就随机：同一个三城问题，6 次里有 2 次它没派，自己搜 3 次就答了。
  - 这套做法可以直接搬到另一个项目 Fusion，它也有同样的问题。
