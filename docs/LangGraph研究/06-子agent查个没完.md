# 06 子 agent 查个没完：别家怎么收住，我们试了哪几种

2026-11-01。

**起因**
子 agent（deepseek-flash）不管任务大小，都会把 12 次模型调用用到头或接近用完。提示词里写了预算（照 Anthropic：简单任务 5 次以内、很难的最多 15 次），它会先给自己定一个，查着查着说"预算还够"，一直用到上限。Fusion 也有同样的问题。

**这篇做两件事**
1. 看别家（框架和公开的研究 agent）怎么让 agent 停下来；
2. 在灵稿上用真实模型试几种做法。

实验代码在 `实验/06-subagent-budget/`，用法写在 `bench.py` 开头。

**复现要钉住代码版本**（11-02 补）：下面"我们的实验"是 0d24e84 的产品代码跑的，"做进产品"那段的端到端是 2c456a3 跑的。2c456a3 起产品默认带 8/8 预算和每步提醒，`bench.py` 的几种做法都建在产品代码上，在之后的代码上跑，每种都会带上 8/8，比的就不是原来那几样了，所以现在脚本会直接退出。要复现，先 `git worktree add` 到 ba1eeea（bench）或 2c456a3（端到端），把 `backend/.env` 拷过去再跑。

## 别家怎么做

读的是源码和原文。源码都下载或浅克隆到本地读，没有运行。

**共同点**
- 所有框架都靠代码硬上限兜底。提示词里写的预算都是"软"的，没有一家只靠提示词。
- 到了上限怎么收尾，分三种：
  - 直接报错或停下，不给答案：OpenAI Agents SDK、Google ADK、LangChain 的限制 middleware（end 模式）；
  - 另外调一次不带工具的模型来写答案：smolagents、open_deep_research、Jina；
  - 根本没有循环，深度和广度由代码定死：GPT Researcher、dzhng/deep-research。
- 灵稿现在用的是第二种：最后一次请求末尾加说明，同时关掉工具。

**各家要点**

- **Anthropic**
  - 来源：工程博客《How we built our multi-agent research system》，以及 claude-cookbooks 的 `patterns/agents/prompts/`。
  - 博客承认早期的 agent 会 "scouring the web endlessly for nonexistent sources"，主要靠在提示词里写"多大的任务用多少次调用"来压。
  - 子 agent 提示词：
    - 最多 20 次工具调用，到 15 次左右就收尾；
    - 用一个 `complete_task` 工具表示查完了；
    - "diminishing returns" 就停。
  - 这些都只是提示词，公开的代码里没有 `complete_task`，也没有 20 次的强制。
- **LangChain open_deep_research**
  - 研究员的提示词把预算写得很紧，停止条件也写得具体：
    - 简单问题搜 2～3 次，复杂的最多 5 次；
    - "已经有 3 个以上相关来源""最近两次搜索结果差不多"就立即停；
    - 每次搜索后调 `think_tool` 反思一下；
    - 有一个 `ResearchComplete` 工具表示查完。
  - 代码上限：研究员最多调 10 次模型。这个数不告诉模型。
  - 到了上限，研究员不再拿到一轮。代码转到 `compress_research`，用另一次模型调用把查到的整理成报告。
  - 主 agent 那边最多 6 轮，一次最多派 5 个。
- **LangChain deepagents 0.7.32**：子 agent 没有任何上限（`recursion_limit` 是 9999）。
- **LangChain 1.4.7 自带的 middleware**
  - `ModelCallLimitMiddleware`：到上限后塞一条假的 AI 消息（"Model call limits exceeded: …"）就结束，模型拿不到最后一轮。
  - `ToolCallLimitMiddleware`：
    - 可以按工具限；
    - continue 模式下，超出的调用收到"不许再调"的报错，模型接着自己决定，但不强制它收尾；
    - end 模式同样是塞一条假消息结束。
- **OpenAI Agents SDK**：`max_turns` 默认 10，超了抛异常。可以挂一个处理函数返回固定的话，但 SDK 不会替你再调一次模型。
- **smolagents**
  - `max_steps` 默认 20。到上限后另调一次不带工具的模型，提示词大意是"一个 agent 想回答却卡住了，请你根据它的记录回答"。
  - 它有一个"还剩几步"的提醒，但模板写错了（单花括号，Jinja 不替换），模型看到的是字面上的 `{remaining_steps}`。
- **Google ADK**：`max_llm_calls` 默认 500，超了抛异常，不给答案。循环用 `exit_loop` 工具结束。
- **Jina node-DeepResearch**：管得最多，基本不让模型自己决定什么时候停。
  - 按 token 算预算。用到 85% 就进入"beast mode"：输出格式只允许答案，模型选不了工具。
  - 代码每一步都会拿掉一些动作：不能连搜两次、攒够 50 个网址就不能再搜、刚搜完不能马上答。
  - 用向量相似度（阈值 0.86）去掉跟之前差不多的查询。
  - 答案要另一个模型评审通过才算数。
- **GPT Researcher、dzhng/deep-research**：不是 agent 循环。先由模型列出 N 个查询，代码截到 N 个，按"广度、深度"递归，到底就写报告。
- **论文**
  - **BATS**（Google，arXiv 2511.17006，《Budget-Aware Tool Use Enables Effective Agent Scaling》）。核心是 Budget Tracker：每次工具结果回来后，紧跟着告诉模型每种工具"用了几次、还剩几次"。
    - 用了它以后，Gemini-2.5-Pro 在预算 10 下的 BrowseComp 成绩（12.8%）和不加时预算 100 的（12.6%）差不多，搜索少了 40%。
    - 注意它解决的问题跟我们相反：它的模型是预算给多了用不完、提前收工。
  - SMART（2502.11435）、OTC-PO（2504.14870）都是靠训练让模型少调工具，我们用不上。

## 我们的实验

**怎么比**
- 输入固定：拿两次真实运行（Rust/Go/Zig、杭州/成都/武汉购房政策）里 Pro 写好的 6 份交代。直接跑子 agent，不经过 Pro，这样每种做法拿到的任务一模一样。
- 每种做法跑一次（6 个子 agent，同时 3 个）。
- 记录每个子 agent 调了几次模型、搜了几次、读了几页、花了多少钱、报告多长、引用多少。
- 质量：让 Flash 当评委，拿每种做法的报告和 base 的同一份逐对比较。每对比两次，第二次交换前后位置。评委按"覆盖任务要的问题、具体、分清确认和计划、带来源"判，规定不能因为长就判好。
- 6 对，每对 2 次，满分 ±12。−12 表示每次都判 base 好。

**几种做法**
- **base**：现在的（Anthropic 的预算说法，写明 12 次上限）。
- **odr**：换成 open_deep_research 研究员的写法（搜索 2～3 / 最多 5 次，加上具体的停止条件），不说代码上限。Flash 每步本来就有思考，`think_tool` 改成"在思考里评估"。
- **cap6**：提示词不动，代码上限 12 → 6。
- **odr2**：odr，再把读页也算进预算（简单 1～2 页，复杂最多 5 页）。
- **tracker**：odr2，加上 BATS 的 Budget Tracker。每次工具结果回来，请求末尾加一条 `<budget>search_web Budget Used: 3, … Remaining: 2 …</budget>`，不存进记录。

**结果**

| 做法 | 每个调模型 | 搜 / 读（6 个合计） | 每个平均用时 | 花费 | 评委（对 base） |
|---|---|---|---|---|---|
| base | 8～12（1 个到顶） | 107 / 20 | 125 秒 | $0.166 | — |
| odr | 4～11 | 38 / 39 | 87 秒 | $0.095 | −8 |
| cap6 | 6（全到顶） | 74 / 16 | 70 秒 | $0.132 | −8 |
| odr2 | 6～10 | 42 / 25 | 99 秒 | $0.101 | −12 |
| tracker | 5～7 | 30 / 26 | 75 秒 | $0.078 | −12 |

另外：
- 粗查关键事实（版本号、发布日期、公积金额度这类）时，几种做法基本都在（只有两处缺）。这张事实表是从 base 的报告里摘的，量的是"别的做法有没有丢掉 base 查到的东西"，不是事实对不对。
- 评委说各做法缺的，大多是细节：补丁版本修了什么、某个区的补贴金额、下一个版本的提案编号。

## 结论

1. **只在提示词里写预算管不住 Flash。** Anthropic 的说法（base）、open_deep_research 的说法（odr、odr2）都试了。
   - odr 的搜索确实少了，但它把省下来的换成了读页（Rust 那个一个读了 16 页）。
   - 把读页也写进预算（odr2）以后，还是有两个各搜了 9 次。
2. **每步把"用了几次、还剩几次"放在请求最后（tracker），6 个子 agent 每个都正好守住了预算**：搜 5 次，读页不超过 5 次，调模型 5～7 次。
   - 这是几种做法里唯一真管用的。
   - 和上次修"最后一步写报告"的道理一样：说明要放在模型正在看的地方（请求末尾），放在系统提示词里它会忘。
3. **查得少，细节就少。** 评委几乎每份都判 base 更全，质量大致跟查的总次数（搜加读）一起走：base 127 次，cap6 90 次和 odr 77 次都是 −8，odr2 67 次和 tracker 56 次都是 −12。
   - 没有哪种写法能少查又不丢东西。
   - tracker 的价值是让"查多少"变成一个真能调的旋钮，以前怎么写它都用到头。
4. **没验证的地方**
   - 缺的这些细节，进不进得了最终回答？主 agent 会把 3 份共 3 万多字的报告压成几千字。
   - 每种做法只跑了一次。
   - 评委是 Flash。
   - 评委规定不判真假，也看不到来源，所以测的是覆盖和具体程度。事实对不对、引用撑不撑得住结论，没测。
   - base 自己跑两次之间差多少（噪声多大）没测。
   - 6 个任务都是"把一段时间的变化列全"这一类。

## 建议（等 Sean 定）

- **机制：用 tracker。**
  - 每次工具结果回来，在请求末尾写上每种工具用了几次、还剩几次。
  - 某种工具用完了，代码就不再执行它（像 `ToolCallLimitMiddleware` 的 continue 模式那样回一句"用完了"）。
  - 总的调模型上限照旧兜底，最后一次关掉工具写报告。
  - 这套 Fusion 也能用。
- **预算定多少，是产品上的取舍：查得深就花得多、等得久。** 几种定法：
  - 固定一个数，比如每个子 agent 搜 8 次、读 8 页。介于这次的 5 和 base 实际用的 16～18 之间，需要再跑一次看看；
  - 主 agent 派活时按这部分要多深，给每个子任务定预算（Anthropic 主 agent 提示词里的"按复杂度定规模"），tracker 照它给的数提醒。
- **下一步要回答的问题：** 少掉的细节到底影不影响用户看到的回答。用 Pro 端到端跑 base 和 tracker（同样两个问题），再比最终回答。约 0.25～0.3 美元一对。

## 花费

- 跑子 agent 5 种做法：$0.57；评委：$0.21。共约 $0.78。
- 搜索服务的 deepseek 额度从 302 用到 585（每天 1000），付费的 Brave 一次没用。

## 2026-11-01 深夜：做进产品，端到端对比

Sean 定了按工具设上限，问能不能借助 LangChain 现成的组件。

**用了 LangChain 的哪些**
- **`ToolCallLimitMiddleware`，continue 模式**：每种工具一个实例，搜索、读页各设一个数。
  - 超了的调用不执行，模型收到 LangChain 写的 "Tool call limit exceeded. Do not call 'search_web' again."。
  - 同一批里没超的照常执行，只拦超出的那几个。
  - 次数记在子 agent 的状态里（`thread_tool_call_count`），跟着检查点存，出错重试接着跑时也接着算。
- **`ModelCallLimitMiddleware` 没用**：到上限后它塞一句话就结束，模型没机会写报告。我们原来的"最后一次关掉工具写报告"保留。

**自己写的**
- **预算提醒**：LangChain 没有，在 `SubagentPrompt` 里加了几行。每次工具结果回来，请求末尾加一条 BATS 原样的 `<budget>`，次数直接读上面那个组件记的。
- **被拦下的调用**：标上 `over_budget`，页面上不列，用量不算。
- **顺手修的**：参数解析失败、没真执行的调用，以前会被算进搜索次数，现在也不算了。

**提示词和配置**
- `[subagent].process` 换成 open_deep_research 研究员的写法（就是上面 tracker 那组用的），数换成配置里的预算，再加 BATS 提示词里"每次工具结果后有 budget"那句。
- 预算是两个环境变量 `SUBAGENT_SEARCH_BUDGET`、`SUBAGENT_READ_BUDGET`，默认 8（11-02 Sean 定）。
- 代码见 `subagent.py` 的 `ToolBudget`、`SubagentPrompt`。

**端到端怎么比**
- 主 agent 用 Pro、子 agent 用 Flash，问题和 bench 一样：Rust/Go/Zig、三城购房政策。
- 三种做法：
  - 现在的：不设预算，ba1eeea 的提示词；
  - b5：每个子 agent 搜 5 次、读 5 页；
  - b8：每个子 agent 搜 8 次、读 8 页。
- 看用户最后看到的回答：Flash 当评委，每份都和参照比两次，第二次交换前后位置。参照是 11-01 用 0d24e84 跑的那次（base0），提示词和"现在的"一样。
- "现在的"重跑一次再和参照比，就能看出评委加上两次运行本身的波动有多大。
- 脚本：`实验/06-subagent-budget/e2e.py`、`e2e_judge.py`。

**结果**

| 问题 / 做法 | 子 agent 搜 / 读（合计） | 每个子 agent 搜 | 用时 | 花费 | 回答字数 | 评委（对参照） |
|---|---|---|---|---|---|---|
| Rust/Go/Zig 现在的 | 32 / 20 | 11、12、9 | 158 秒 | $0.073 | 7056 | +2 |
| Rust/Go/Zig b5 | 15 / 15 | 5、5、5 | 151 秒 | $0.055 | 5313 | −2 |
| Rust/Go/Zig b8 | 23 / 20 | 7、8、8 | 147 秒 | $0.070 | 4474 | −2 |
| 三城 现在的 | 80 / 2 | 24、31、25 | 257 秒 | $0.123 | 3516 | −2 |
| 三城 b5 | 15 / 12 | 5、5、5 | 154 秒 | $0.062 | 3552 | −2 |
| 三城 b8 | 24 / 11 | 8、8、8 | 176 秒 | $0.086 | 3091 | −2 |

参照的两份回答：Rust/Go/Zig 6582 字，三城 4100 字。

**看到的**
1. **预算每次都守住了。** b5、b8 的每个子 agent 都没超；b8 有的没用满（读页 2 页就停）。
2. **省多少，看"现在的"跑没跑飞。**
   - 三城那次跑飞了：每个子 agent 搜了 24～31 次（一次并行搜三四个，调模型次数不多，搜索次数很多）。设了预算以后：
     - b8（最后定的）：用时 257 → 176 秒，降 32%；花费 $0.123 → $0.086，降 30%；
     - b5：用时 154 秒，降 40%；花费 $0.062，降一半。
   - Rust/Go/Zig 那次"现在的"本来就没跑飞（每个 9～12 次），b8 和它花费差不多，时间三种都在 150 秒左右。端到端的时间主要花在 Pro 写回答上。
3. **有覆盖变少的信号，但分不清是预算造成的，还是运行本身的波动。**（11-02 改：原来写的是"评委分不出差别、只看出长短"，说过头了）
   - b5、b8 四次比较全输。评委列的缺项是实在的内容，有的是整块：
     - b8 三城缺了税费、落户、全国首套贴息、房贷 40 年；
     - b5、b8 的 Rust/Go/Zig 缺了 Rust 1.98 的破坏性变更、Go 的升级坑（`GODEBUG`、`//go:linkname` 收紧）这类迁移风险。
   - 但"现在的"重跑一次，三城那题也是两次都输，缺的同样有落户、现房销售细则、税费细则。每种只跑了一次，分不开。
   - 6 次比较里赢的都是长的那份。是长的确实覆盖得多（上面的缺项看着像），还是评委偏长，这次也分不开。回答写多长主要看 Pro 这一次怎么写（b8 查得比 b5 多，回答反而更短）。
   - 粗查 Rust/Go/Zig 的关键版本号：b5 少提了 Go 1.27.1，b8 少提了 Rust 1.100 和 Zig 0.18，主干都在。这些版本号也是从参照里摘的。
   - 评委规定不判真假，也看不到来源。事实准不准、引用撑不撑得住结论，这次没测。
4. **另外两次三城（b5、b8 各一次）Pro 根本没派子 agent，自己搜 3 次就答了**（30 秒左右，约 $0.015）。主 agent 看到的提示词三种做法完全一样，这是 Pro 自己的随机判断，跟预算无关。这两次没算进对比，又各重跑了一次。

**结论**
- 机制可以定下来：预算一定守得住，主要作用是把跑飞的情况收住，正常情况下花费差别不大。
- 少查对最终回答影响多大，这次定不了。有覆盖变少的信号（设了预算的四次全输，缺的有整块内容），但同一版重跑也会两次都输，每种只跑一次分不开；准确性没测。要测准，得每种跑好几次，再独立列一张这道题该有的事实清单（不从哪一份回答里摘），逐条对，顺带核对引用。
- 默认数先填 8/8，等 Sean 定。11-02 Sean 定了就用 8/8，每个子 agent 都一样，不让主 agent 按任务分别设（Sean：动态设置感觉会出问题）。

**花费**：端到端 8 次运行 $0.50，评委 $0.04，共约 $0.54。搜索服务付费的 Brave 一次没用。
