# 02 检查点：存了什么、Postgres、时间回溯

2026-10-31。读的是装好的源码（langgraph 1.2.18、langgraph-checkpoint 4.3.1、langgraph-checkpoint-sqlite 3.1.2、langgraph-checkpoint-postgres 3.2.0）。实验在进程里直接跑灵稿的对话图：假模型、假网关，读页正文放大到 6000 字，接近真实大小。代码在 `实验/02-checkpoint/exp.py`，用法写在文件开头。

## 一个检查点里有什么

`langgraph/checkpoint/base/__init__.py` 里的 `Checkpoint`：

- `id`：时间有序的 uuid，按 id 排序就是先后顺序。另有一个时间戳 `ts`。
- `channel_values`：每个通道当时的值。对我们来说就是 `messages`、`title`、`turns`。
- `channel_versions`：每个通道的版本号，每写一次加一。
- `versions_seen`：每个节点看过各个通道的哪个版本。LangGraph 靠它判断下一步该跑哪个节点。

`CheckpointMetadata`：

- `source`：input、loop、update、fork 之一。update 是 `update_state` 写的，fork 是分叉出来的。
- `step`：第几步。
- `parents`：父检查点。
- `run_id`：哪次运行写的。

检查点之外还有一张 writes 表，存的是每一步里各个任务写出的结果（pending writes）。它的作用是：一步里有好几个任务（比如并行的几个工具调用），其中一个失败了，做完的那些结果已经存下，重试时不用重做。我们 `stop_turn` 的注释里说的就是这个。

**每走一步存一个检查点。** 我们的对话每轮 10 到 12 个，因为每个 middleware 钩子都算一步。实测一轮"直接答"：`update0 → loop1 → … → loop11`。8000 上最大的对话 5 轮 50 个检查点，正好对得上。

## 存储为什么按平方增长

SqliteSaver 把所有通道的值都放在检查点那一行里。源码注释原话（`sqlite/_delta.py`）："No separate blob table — `channel_values` lives inline in the checkpoint"。所以每个检查点都是整份消息的一份拷贝，对话越长，每份越大，份数也越多。

8000 的真实数据（只读复制出来查的）：

- 最大的对话 5 轮、25 条消息，存了 50 个检查点，共 5.4MB；
- 它最新的状态只有约 200KB，差了 27 倍；
- 17 个对话一共 16MB。

实验：连说 12 轮，每轮搜一次、读一页（`growth`、`growth-exit`）：

- SQLite（现在的做法）：144 个检查点，12.8MB。
- Postgres：6.6MB。通道的值单独放在 `checkpoint_blobs` 表，按“通道 + 版本”存，没变的通道（比如标题）不重复存；但消息几乎每一步都在变，所以还是按平方增长。
- SQLite + DeltaChannel：1.1MB。
- Postgres + DeltaChannel：0.9MB。
- SQLite + exit 模式：24 个检查点，2.1MB。
- SQLite + exit + DeltaChannel：0.56MB。
- 读一次当前状态，各种组合都在 1 到 2ms。在这个规模下，DeltaChannel 重建消息不慢。

## DeltaChannel（beta）

`langgraph/channels/delta.py`：

- **机制**：检查点里只给这个通道存一个占位。它的值靠沿着父检查点往回走、按顺序重放 writes 表里的写入来重建。每更新 `snapshot_frequency` 次（默认 100，实验里用 20）存一次全量快照，免得往回走太远。
- **用法**：在 `state_schema` 里把 `messages` 标成 `Annotated[list[AnyMessage], DeltaChannel(reducer)]`。`create_agent` 会让调用方传的 `state_schema` 优先，源码注释专门提到了这个用法（`langchain/agents/factory.py`）。
- **reducer**：一次收一批写入，要求分几批处理和一次处理完结果一样。我们用的是 `reduce(add_messages, writes, state)`。
- **注意**：
  - 还是 beta，接口和存储格式都可能变。
  - Postgres 的 `prune(keep_latest)` 遇到用了 DeltaChannel 的线程直接拒绝。
  - 分叉在 DeltaChannel 下也正常（实验 `fork+delta`）。

## 持久化模式（durability）

- **sync**：每一步的检查点写完才走下一步。
- **async**（默认，我们现在用的）：检查点在后台写，下一步同时开始。
- **exit**：只在运行结束时写一次。正常结束、出错、被打断都算结束。

实测：

- 一轮下来，sync 和 async 都是 12 个检查点，exit 是 2 个：用户的话写进去那一个，加上结束时那一个（`durability`）。
- exit 下中途出错，退出前照样把进度写下来（`next=['tools']`，做完的搜索留着），重试能从断点接着跑，和 async 一样（`retry`：读页时网关鉴权失败）。
- exit 的代价是：进程直接崩掉或被杀（不是 Python 异常）时，这一轮跑到一半的都没存，只剩用户那句话，重试要从头跑这一轮。
- 没验证：在我们的运行器里，exit 下点停止时的收尾对不对。`stop_turn` 是靠 `get_state` 拿已经做完的结果的。
- 2026-11-02 已经改成 exit（`ResearchRunner._graph_events`），停止也验证了：主 agent、子 agent 中途停下，做完的搜索、读页都留着（子 agent 出错退出时自己的检查点也会写，见 LangGraph `_suppress_interrupt`）。每轮存 3 份：用户的话、结束、推荐问题。执行中页面要的来源改成跟着做完的那一步推过去。

按轮分叉只需要轮与轮之间的两个检查点：用户的话写进去的那个，和上一轮结束的那个。exit 两个都留，所以不影响按轮做时间回溯。

## 时间回溯

### 机制

- `get_state_history` 按从新到旧列出所有检查点，每个都带父检查点。
- **从旧检查点接着跑**：`stream(None, 那个检查点的 config)`。它之前的步骤不重跑，之后的重新跑。LangGraph 会先写一个 `source=fork` 的检查点，作为新分支的起点（`pregel/_loop.py`）。
- **在旧检查点上 `update_state`**：会写一个新检查点（`source=update`），它的父检查点就是那个旧的，再从它接着跑。这也是分叉。
- **没有“当前分支”这个概念**：`get_state` 不指定检查点时，取 id 最大的那个，SQL 就是 `ORDER BY checkpoint_id DESC LIMIT 1`。谁最新，谁就是当前。

### 实验（`fork`，3 轮）

- **重新回答**：从“第三问刚写进去”的那个检查点（运行器 `update_state` 写的）接着跑。新回答成了当前状态；旧回答按它的 checkpoint_id 还能取到。
- **改原话**：在第三问写进去之前的那个检查点上，用 `update_state` 写入新的话，再接着跑，就分出一个新分支。
- **列分支**：按父检查点分组，孩子多于一个的就是分叉点。3 轮加两次分叉，找到了两个分叉点。
- **切回旧分支**：在旧分支的末端写一个空更新（`update_state(旧末端, None)`），它就成了最新的，当前状态切回原来的第三问。
- 检查点从 18 个涨到 31 个。
- 假模型每次回答都一样，所以“重新回答”前后看不出文字差别，只能靠检查点 id 区分；“改原话”那条能看出差别。

### 对照我们现在的重新回答

现在的做法是：用 `RemoveMessage` 删掉这一轮之后的消息，改掉 turns 里的记录，再删掉这一轮画的图。改成分叉以后：

- 什么都不删，旧回答留着。turns、title 本来就在状态里，会跟着分支走。
- 画的图不能再删，因为旧分支还在用。只有删对话时才能删图。
- 要列出一轮有几个版本，不能用 `get_state_history`，它会把所有检查点都反序列化，12 轮就是 12.8MB。得像 `thread_ids` 那样直接查表，只看 `checkpoint_id` 和 `parent_checkpoint_id`。
- 切回旧版本有两种做法：写一个新检查点；或者运行器自己记住“当前在哪个检查点”，以后每次都带着 checkpoint_id 跑。
- 分叉越多，存储越大，而且和“只留最新”的清理方式冲突。

## Postgres

- 一共四张表：
  - `checkpoint_migrations`；
  - `checkpoints`：checkpoint 字段是 JSONB，不含大的通道值；
  - `checkpoint_blobs`：通道的值，按“通道 + 版本”存；
  - `checkpoint_writes`。
- **清理**：有 `setup()` 建表，有 `delete_thread`、`prune`（keep_latest 或 delete）。SqliteSaver 只有 `delete_thread`。
- 基类里还有 `delete_for_runs`、`copy_thread`，SQLite 和 Postgres 两个实现都没做。Agent Server 的回滚和复制线程要用到这两个，它的正式版用的是自己的存储。
- 我们的 `thread_ids` 直接查表，换成 Postgres 时照着写一份就行：`checkpoints` 表同样有 `thread_id`、`checkpoint_ns` 两列。
- 同步版 `PostgresSaver` 可以直接传一个连接池（`psycopg_pool.ConnectionPool`），接得上我们的线程池写法。异步版是 `AsyncPostgresSaver`。
- 传了连接池，它的每次读写也还是持着自己的一把锁（`_cursor` 里的 `with self.lock`），同一时刻只有一个读写，和 SqliteSaver 一样。池子的用处是连接断了能换新的。
- 实验用的是 pgserver（一个 pip 包，里面带了 Postgres）在临时目录里起的库，没用 Docker。

## 建议（等 Sean 定）

1. **存储**：现在 16MB 还不急，但对话越长，增长越快（按平方）。
   - （2026-11-02 Sean 定了改成 exit，已上线，见上面“持久化模式”。）
   - 最省事、风险最低的是改成 exit 模式：只改一个参数，存储少大约 6 倍，按轮分叉和出错重试都不受影响。代价是进程崩掉时这一轮要从头跑。另外，exit 下点停止的收尾还要在运行器里验证一次。
   - 后来发现它不只是后端的事。页面在执行中会重新取状态：搜索、读页做完后取新来源，正文里的引用靠它才显示成编号；起好标题后侧栏要刷新。exit 下执行中什么都不落库，这两样都要等这一轮结束才出来。要用 exit，得先把来源跟着事件一起推给页面。
   - DeltaChannel 能再省 4 倍，但还是 beta，先不用。
   - 不要用 `prune(keep_latest)` 这类“只留最新”的清理，它会把时间回溯要用的历史删掉。
2. **部署到 dev**：用同步版 PostgresSaver 加连接池，本机继续用 SQLite。按 [部署目标](../调研场景与多场景架构设计.md) 的规划，接口本来就是可替换的。
   - Sean 定了要换，而且本机开发也连 dev 上的库，省得每次都等 CI。2026-10-31 已做：`open_postgres_checkpointer`。
   - 库是这样分的：本机验证用 `lingdraft_local`，部署出去的实例用 `lingdraft`。分开的原因有两个：图存在各自机器的磁盘上；“一个对话同时只跑一次”是在各自进程里登记的，两个进程共用一个库就管不住对方。
   - 实测：本机经 SSH 隧道读一次状态约 20ms，列对话约 30ms。隧道断了请求会等 10 秒报错，接回来自己就好了。
3. **重新回答改成分叉**：技术上可行。要不要做“1/2 切换看旧回答”是产品决定：要做就改成分叉；不做的话，现在删消息的做法更简单，没必要改。
