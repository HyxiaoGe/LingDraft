# 面试笔记：对话运行器和检查点（对照 LangGraph Agent Server）

2026-11-03 整理。细节、源码位置和全部实验见 [01-Agent Server对照.md](01-Agent%20Server对照.md)、[02-检查点.md](02-检查点.md)。

## 一句话版本

灵稿的对话 agent 跑在 LangGraph 上，但“一个对话一次只跑一轮、停止、断线续看、回答时又发了话”这些运行层的事，是我们在框架外面自己写的。我把 LangGraph 官方的运行层 Agent Server 搭起来逐项对照，学了它的设计：每次执行存进库能查；回答时又发的话排队等这一轮答完。还多做了一种它没有的：把这句话插进正在跑的这一轮。顺着往下研究检查点，发现存储按对话长度的平方增长，改成只在一轮的开头和结尾存（`durability="exit"`），存储降到原来的四分之一到六分之一。

## 背景

- **系统**：灵稿的对话 agent，用 LangChain `create_agent` 搭（底层是 LangGraph），挂了 4 个 middleware。主模型 DeepSeek V4 Pro，能搜、能读网页、回答里标来源，复杂问题派子 agent 并行去查。
- **写法**：FastAPI，同步写法，图在线程池里跑，页面靠 SSE 收事件。检查点在 dev 上存 Postgres。
- **LangGraph 管的**：图怎么一步步跑、每一步存检查点。
- **我们自己写的运行器**（`app/api/research_runner.py`）：
  - 登记表：一个对话同时只跑一次；
  - 线程池：同时跑几个对话（默认 4 个），多的排队；
  - 事件日志：每次执行的事件带序号，断线后从序号接上；
  - 停止和停止后的收尾。
- **Agent Server** 是 LangGraph 官方的运行层，管的正好是这一块。生产环境自己部署要 LangSmith 许可证，所以定位是学设计、做对照，不迁过去。

## 一、运行器：和 Agent Server 对照

### 怎么对照的

- 把灵稿的对话图原样挂到 `langgraph dev`（内存版，免费）上，用假模型、假网关和 langgraph-sdk 逐项试：双发、停止、断线续看、重新回答、并发。
- 挂上去本身就踩了两个坑：
  - 它每次运行的 context 只能是 JSON，我们的 context 里放的是对象（图片存储、停止检查），构造直接失败；
  - 它用异步跑图，middleware 必须有异步版。实验里写了一层桥才跑通。
- **结论：方向没跑偏。**
  - 我们的登记表相当于它的 reject 策略；
  - 我们的事件日志相当于它的可续看流（它的事件 id 和 Redis Stream 一个格式，我们的接口也是按“以后换 Redis”写成可替换的）；
  - 我们的停止相当于它的 interrupt，再加上我们自己的收尾。
- 它多出来、值得学的有三样：run 落库、双发策略、从检查点分叉。

### 1. 每次执行存进库

- **问题**：执行登记只在进程内存里，跑完就没了。检查点里只留最近一次错误，重试成功就被覆盖了。出错时日志里也没东西。线上出了问题，事后无从查。
- **做法**：学它的 run，加了一张运行记录表：
  - 每次执行一行：怎么来的（新对话、接着说、重试、重新回答……）、属于哪一轮、状态、进来、开始、结束的时间、错误类型和堆栈、部署的提交号。
  - 服务启动时，把上次还在排队、在跑的记成 lost。
  - 写记录失败只打日志，不影响执行。
  - 只读接口按对话查，排查问题用，页面不用。

### 2. 回答时用户又发了话（double-texting）

**Agent Server 的四种策略**，同一个场景各试了一次（第一句正在慢慢搜，1 秒后发第二句）：

- reject：第二句被拒，409。
- enqueue（默认）：第二句排队，第一轮跑完自动接着跑。
- interrupt：第一轮停在最后一个检查点，第二句马上跑。结果是两句用户的话在消息里挨着，第一轮没有回答，还留下了悬空的工具调用（见下面“停止”）。
- rollback：第一轮连同它的输入整个撤掉，像没说过。

我们原来只有 reject。后来做了两种。

**排队（对应 enqueue）**

- **规则**（产品定的）：
  - 没发出去的话最多一句。排着的时候发不出去，要先撤回（或在输入框里按 ↑ 取回）改好再发。
  - 排着的时候点停止，这一轮停下，排着的照发。
  - 这一轮出错，排着的不发，放回输入框，用户先重试。
- **存在库里**（`pending_messages` 表），服务重启也不丢。
- **难点是交接时的竞态。**
  - 场景：用户排一句话的那一刻，这一轮正好结束。
  - 如果排队时先查“在不在跑”、再写进库，中间这一轮结束了，就没人去发这句话。
  - 做法：“查在不在跑 + 写进库”，和一轮结束时的“退掉占位 + 取走排着的话 + 直接占上位发成新的一轮”，放在同一把锁里。所有占位操作（发话、重试、重新回答、删除）都经过这把锁。占位直接交接，中间别的请求插不进来。
- 排着话的这一轮不起推荐问题，因为马上就有新的一轮。

**插进这一轮（Agent Server 没有）**

- **场景**：模型正在搜，用户发现方向不对，想补一句“只看比亚迪”。既不想停掉重来，也不想等它答完。
- **做法**：
  - 在主 agent 的 middleware 里用 `before_model` 钩子，每次调模型之前看有没有等着插的话。
  - 有的话，就作为一条用户消息接在工具结果后面，同时发一个事件，让页面把它显示在这一轮的过程里。
  - 模型接着做时就看得到它，仍然是同一轮。
- **为什么挂在 `before_model`**：这是模型做下一个决定之前的最后一个点，工具执行到一半是插不进去的。代价是要等手上这一步做完；派了子 agent 的，要等子 agent 都做完。
- **几个关键细节**：
  - **打标记**：我们是按用户消息划分一轮的。找这一轮从哪开始、重新回答从哪重来、内容审核拦下时去掉哪一轮，都靠它。插进来的也是用户消息，不打标记就会被当成新一轮的开头。所以给它加了一个标记，划分轮次的几个函数都跳过它。
  - **来不及插**：模型已经在写最后的回答，不会再调模型，这一轮就结束了。结束时把没插进去的话退回排队，照常发成新的一轮。
  - **先确认模型接口**：DeepSeek 思考模式下，工具结果后面直接接一条用户消息，会不会报 400？模型会不会理它？花 2 次调用试了：不报错，模型把它当成用户的新要求，改成只查比亚迪。所以不用再包一层提示词。
  - 插进来的话被内容审核拦下，按“用户的话没通过”处理。
  - 重新回答、改最后一句时，从这一轮用户的原话重来，插的话不保留。
- **真实模型验证**（dev）：问 10 月新能源车销量靠前的几个品牌，搜着的时候插进“只说比亚迪一家就行，别的品牌不用列”。最后只讲了比亚迪，整个过程还是一轮。

**没做的**：

- rollback：停止加上编辑最后一句，已经能做到“换一句重来”，聊天产品里也没见过撤销。
- interrupt：它会留下没回答的一轮和悬空的工具调用，体验和数据都不干净。

### 3. 停止，以及停止后的收尾（Agent Server 不替你做）

- **Agent Server 的 interrupt，实测**：取消几乎是 0 秒生效，但是：
  - 已经流出来、还没进检查点的正文丢了；
  - 模型发起了工具调用、工具还没返回的，消息里留下一个悬空的工具调用（有调用，没结果）。DeepSeek 这类接口要求工具调用后面必须跟着结果，下一次请求就会报错。它的文档也提醒了，要图自己处理；
  - 我们的 `after_agent` 没跑，这一轮没收尾。
- **我们的做法**：
  - 停止检查在下一个流片段、或下一步开始时抛异常。不是立刻停，要等当前的工具做完；画图例外，它边等边查。
  - 然后 `stop_turn` 收尾：
    - 已经流出来的正文存成这一轮的回复；
    - 悬空的工具调用补上结果；
    - 这一轮标成已停止；
    - 子 agent 停在半路的，把它已经查到的来源列给主 agent，下一轮用得上。
- **两边共同的限制**：同步的工具在线程里跑，谁都杀不掉，取消的只是“等待”。

### 4. 断线续看

- 每次执行的事件带序号，进程里留最近 64 次执行的事件，页面带着序号接上。刷新、换个页面打开、断线重连，看到的都一样。
- 接口写成可替换的，以后多实例部署时可以换成 Redis。

### 为什么不直接换成 Agent Server

1. 生产环境自己部署要 LangSmith 许可证。
2. 我们是同步写法，要先把 middleware、模型客户端全改成异步。
3. 页面的事件格式也要跟着换。

值得借的是它的设计，不是它的代码。

## 二、检查点

### 1. 一个检查点里有什么

- 每个通道当时的值（我们的是 `messages`、`title`、`turns`）、每个通道的版本号，以及每个节点看过哪个版本（LangGraph 靠这个决定下一步跑谁）。
- 元数据：来源（input、loop、update、fork）、第几步、父检查点、哪次运行写的。
- 另有一张 writes 表，存一步里各个任务写出的结果。一步里有几个并行的工具调用，其中一个失败了，做完的结果已经存下，重试时不用重做。
- **默认每走一步存一个。** 我们每个 middleware 钩子都算一步，一轮 10～12 个检查点。

### 2. 存储为什么按平方增长

- SqliteSaver 把所有通道的值放在检查点那一行里，每个检查点都是整段对话的一份拷贝。对话越长，每份越大，份数也越多。
- 本机真实数据：最大的对话 5 轮，存了 50 个检查点，共 5.4MB；它最新的状态只有约 200KB，差了 27 倍。
- 实验，连说 12 轮，每轮搜一次、读一页（读页正文放大到 6000 字）：
  - SQLite（原来的做法）：144 个检查点，12.8MB；
  - Postgres：6.6MB。它把通道值单独存，没变的通道不重复存，但消息几乎每一步都变，所以还是按平方涨；
  - 加 DeltaChannel（只存增量）：约 1MB；
  - 改成 exit：24 个检查点，2.1MB。

### 3. 选了 exit 模式

- **几个选项**：
  - DeltaChannel 最省，但还是 beta，接口和存储格式都可能变。
  - `prune`（只留最新）会把出错重试、时间回溯要用的历史删掉。
  - `durability="exit"` 只改一个参数：只在一轮结束时写一次检查点，正常结束、出错、被打断都算结束。
- **出错也不丢进度**：exit 下中途出错，退出前照样写下进度，重试从断点接着跑。
- **代价**：进程被杀或崩掉时（不是 Python 异常），这一轮做到一半的没存，重试要从头跑这一轮。
- **隐藏的坑：这不只是后端的事。**
  - 页面在执行中会重新取状态：搜完、读完取新来源，正文里的引用靠它显示成编号；起好标题后侧栏要刷新。
  - exit 下执行中库里什么都没有，这两样都要等一轮结束才出来。
  - 改法：做完的那一步，事件里带上这一步得到的来源；标题以事件为准。页面不再在执行中取状态。
- **停止要重新验证**：收尾靠读出已经做完的结果。验证了主 agent、子 agent 中途停下，做完的搜索、读页都留着（子 agent 出错退出时，LangGraph 也会写它自己的检查点）。
- **结果**：每轮只存 3 份（用户的话、这一轮结束、推荐问题）。在产品代码上用假模型连说 12 轮：156 个检查点约 4.5MB → 36 个约 1.1MB。

### 4. Postgres

- 用同步版 `PostgresSaver` 加连接池，正好接上线程池的写法。
- 注意：传了连接池，它的每次读写也还是持着自己的一把锁，同一时刻只有一个读写。池子的作用是连接断了能换新的，不是并发。
- 本机开发也连 dev 上的 Postgres，但和部署的实例分开两个库。原因有两条：
  - “一个对话同时只跑一次”是登记在各自进程内存里的，两个进程共用一个库就管不住对方；
  - 图片存在各自机器的磁盘上。
- 本机经 SSH 隧道读一次状态约 20ms，列对话约 30ms。

### 5. 时间回溯（研究了，没用上）

- **机制**：从旧检查点接着跑就是分叉。LangGraph 没有“当前分支”的概念，id 最新的那个检查点就是当前。
- **能做什么**：ChatGPT 那种“1/2 切换看旧回答”。
- **代价**：
  - 要管分支，页面得知道当前在哪条分支上；
  - 画的图不能再删，旧分支还在用；
  - 列一轮有几个版本不能用 `get_state_history`，它会把所有检查点都反序列化（12 轮就是 12.8MB），得直接查表。
- **结论**：这是产品决定，定了不做。重新回答还是删掉这一轮之后的消息再跑。

## 可以讲的知识点

1. **框架给的是机制，产品语义要自己补。** interrupt 能停，但停下以后正文丢了、工具调用悬空，下一次请求直接报错。“停下以后对话还是干净的”这件事框架不管，得自己写收尾。
2. **并发的交接要放进同一把锁。** “查状态”和“写入”分两步做，中间就有窗口。排队的话会不会丢，取决于结束一轮和排进一句是不是互斥的。
3. **看存储，要看它怎么存，不能只看当前状态有多大。** 最新状态 200KB，库里却是 5.4MB，差在每一步都存了一份整段对话。
4. **改持久化方式之前，先找出谁在执行中读状态。** exit 在后端只是一个参数，但页面的引用编号、侧栏标题都依赖执行中能读到状态。
5. **用最便宜的实验先确认行为。** Agent Server 用假模型对照；工具结果后面接用户消息会不会报错，花 2 次调用先试，再动手写。
6. **接口按“可替换”拆。** 登记表、事件日志、检查点、运行记录都是接口加几种实现（内存、SQLite、Postgres），本机、测试、dev 各用各的，换存储不动上层。
7. **技术上能做，不等于要做。** 分叉、撤销都能做，但要不要，是产品决定。“没发出去的话最多一句”也是：要么真的支持多条，要么就一条，不做“两个位置”“自动合并”这类让用户看不懂的中间状态。

## 两分钟讲法

> 灵稿是一个能搜、能读网页、标来源的对话 agent，底层用 LangGraph。LangGraph 只管图怎么一步步跑，一个对话一次只能跑一轮、停止、断线续看、回答时用户又发了话，这些运行层的事是我自己写的。
>
> 我把 LangGraph 官方的运行层 Agent Server 搭起来，用假模型逐项对照，发现我们的设计基本对得上，也学了它两样：每次执行存进库，能查历史和失败原因；用户在回答时又发的话，先排着，这一轮答完再发。排队最难的是交接：话排进来的那一刻这一轮正好结束，就可能没人发。我把“排进来”和“一轮结束时取走并发出”放进同一把锁里，占位直接交接。
>
> 我还多做了一种它没有的：把排着的话插进正在跑的这一轮。在每次调模型之前的钩子里，把它作为一条用户消息接进对话。这里要注意，我们是按用户消息划分轮次的，所以要给它打个标记，不然会被当成新的一轮。动手之前我先花两次调用确认了 DeepSeek 接受工具结果后面跟用户消息。
>
> 对照时还发现，它的 interrupt 停下以后会留下悬空的工具调用，下一次请求就报错，这个收尾框架不管，我们自己做了。
>
> 顺着往下研究检查点，发现存储按对话长度的平方增长：一个 5 轮的对话最新状态才 200KB，库里存了 5.4MB，因为每一步都存一份整段对话。我把持久化改成只在一轮结束时写，存储降到四分之一到六分之一。这一步的坑在页面：页面原来在执行中读状态显示引用编号，改了以后读不到，所以把来源改成跟着事件推过去。

## 可能被追问的

- **为什么不直接用 Agent Server？**
  三个原因：生产部署要许可证；我们是同步写法，要先全面改成异步；页面的事件格式也要换。它的设计值得借，我们的运行器接口也是按同一条线拆的，以后真要换，代价不大。

- **排着的话会不会丢？**
  存在库里，服务重启也在。交接放在锁里，见上面。出错的那一轮不发，放回输入框，用户自己决定重试完再不再发。

- **插进来的话为什么不打断正在跑的工具？**
  同步工具在线程里跑，本来就杀不掉；而且模型只在调用之间做决定，工具跑到一半插进去，它也看不到。所以就在下一次调模型之前放进去。代价是要等手上这一步做完。

- **为什么用用户消息，不用系统提示？**
  试过，DeepSeek 接受工具结果后面直接跟用户消息，也会照着改。用户消息语义最准确，就是“用户又说了一句”，不用另写一段提示词去解释。

- **模型已经在写最后的回答了怎么办？**
  `before_model` 不会再触发，这一轮就结束了。结束时把没插进去的话退回排队，发成新的一轮，不会丢。

- **为什么停止不是立刻停？**
  要等当前的工具做完，因为同步工具杀不掉；画图要等很久，单独做成边等边查。停下以后要保证对话是干净的：正文留着，悬空的工具调用补上结果，不然下一句就报错。

- **exit 的代价能接受吗？**
  只有进程直接崩掉或被杀时，这一轮要从头跑；普通的出错、点停止都不受影响。换来存储降到四分之一到六分之一，而且它不按平方涨了。

- **为什么不用 DeltaChannel？不是更省吗？**
  更省，但还是 beta，接口和存储格式都可能变，存进去的数据以后不一定读得出来。exit 是稳定功能，先用它；DeltaChannel 稳定了可以再叠上去。

- **为什么不定期清理旧检查点？**
  `prune` 只留最新，会把出错重试、时间回溯要用的历史删掉。exit 是从源头少存。

- **两个页面同时开着同一个对话呢？**
  老实说只靠锁和事件序号兜着：执行换了，页面就清掉实时内容，重新接。没专门测过“刷新正好卡在交接那一刻”这种情况。

- **这些怎么测的？**
  - 假模型加一个门闩：让模型停在第几次调用上，就能稳定复现“插得进去”和“来不及插”这两种时机。
  - 交接、停止、出错、内容审核拦下、撤回、重启，各有测试。
  - SQLite 和 Postgres 两种库都跑整套测试。
  - 测试过程中还发现假模型自己的 bug：消息 id 按条数生成，去掉被拦的一轮以后，新消息的 id 和旧的重复，把旧消息覆盖了。

- **还有什么没验证的？**
  - 进程被杀以后从头跑这一轮：只有测试，没在真机上杀过进程。
  - 派了子 agent 时，插的话要等子 agent 都做完才进对话：是按代码推断的，没单独测。
