# 调研场景问题梳理（供讨论）

日期：2026-10-28。写这份文档的目的是把调研场景目前暴露出来的问题、根因和可选方向摆出来，供 Sean 和 Codex 一起讨论。不是决策文档，没有定案。

相关代码：`backend/app/graph/research/`（图）、`backend/app/research_llm.py`（模型调用）、`backend/app/api/research_runner.py`（接口）、`frontend/src/research.jsx`（前端）。设计与实施记录见《调研场景与多场景架构设计》第 13～16 节。

## 1. 现状：流程是怎么跑的

每个请求都走同一条固定链路，顺序和节点写死在图里：

```
intake（提范围 + 澄清问题）
  → confirm_scope（有澄清问题才弹卡；10-27 之前是无条件逐项确认）
  → plan（策划提示词：拟 3～4 章）
  → research_section × N（每章一个 create_agent 循环：最多 3 次搜索、3 次读原文、20 次模型调用；要求产出 4～8 条论断）
  → confirm_outline（大纲 + 论断确认卡，必经）
  → write（逐章成文，每句挂论断）
  → check（六项检查，只报告不回补）
  → review（终审卡，必经；排除来源 / 改论断 / 重写某章 / 回到大纲 / 批准）
  → export
```

HITL 点有四个：范围澄清、调研中 agent 提问（ask_user，走 HumanInTheLoopMiddleware）、大纲确认、终审。其中大纲确认和终审是每个请求必经的。

## 2. 跑出来的问题（都有真实线程可查）

### 2.1 范围卡明知故问（已改，但根因有代表性）

线程 b501b903 等。需求"最近新加坡的天气情况如何？"被拆成研究问题、时间"最近"、地域"新加坡"三项，逐项弹卡让用户确认。intake 提示词写的就是"只提取用户明确说了的"，所以卡片里每一项必然是原话复述，按设计就是明知故问。

10-27 已改（提交 3ca9170）：只提取原话不确认；模型判断需求模糊才提最多 2 个澄清问题；没有问题整个步骤跳过。真实模型验证：天气题和海报调研题零提问，"帮我调研一下大模型的落地情况"问了行业和地域两个问题。

根因不只是这一张卡：**流程是按"把 HITL 环节展示出来"设计的，不是按"模型什么时候真的需要人"设计的。** 下面的问题是同一个根因的另一种表现。

### 2.2 问天气要跑四章、三分多钟

线程 03b818b1："最近新加坡的天气情况如何？"

| 指标 | 值 |
|---|---|
| 从发出到大纲确认卡 | 3 分 18 秒（15:30:14 → 15:33:32） |
| 章数 | 4：近期天气实况 / 当前天气与预警 / 未来天气预报 / 天气成因与出行影响 |
| 来源 | 69 条 |
| 论断 | 22 条 |
| agent 提问 | 0 次 |

对照 WorkBuddy 同类问题：36 秒，不问任何问题，直接给一句结论 + 实时数据表 + 预报要点 + 可视化卡 + 折叠的 9 个来源，末尾一句"要不要做成每天推送"的追问。

原因是策划提示词写死"3～4 章"，每章都跑完整 agent 循环且要求凑论断数量，没有任何一步能按问题大小缩短或跳过。

### 2.3 真实模型从未调用过 ask_user

所有真实线程（c25e4e89、03b818b1、4b6281a2 及更早的 CLI 线程）asks_used 都是 0。agent 中途提问的路径只在假模型上验证过。这意味着：

- "模型发现问题比想的复杂时自己提出来"目前没有证据支持，不能把它当成兜底。
- 提示词里对 ask_user 的使用条件（术语歧义、来源矛盾、范围要收窄）要么没触发，要么模型不愿意用。没有定位过是哪种。

### 2.4 质量检查在事后、只报不补

check 节点在报告写完后跑六项检查（论断有来源、无排除来源、推断已标记、来源信息完整、无失去来源的论断、时间范围），结果只是展示给用户。写之前没有"问题的每一部分都有事实支撑吗"这种覆盖检查，空缺会被写成推断交出去。

### 2.5 其他已知但没处理的

- 第三章曾触发每章模型调用上限（14 次）导致没产出 Findings，上限提到 20 后没再复现，也没有触顶后的兜底。
- 整线程提问上限 6 次是 Claude 自己加的，没经 Sean 确认。
- 四章串行，互不依赖却不并行。
- 调研期间前端只有每章一行进度，没有工具调用级别的进度。

## 3. 根因判断

一句话：**外层图把"每个问题都是一篇多章报告"写死在控制流里，模型再聪明也绕不开。**

具体是三件事叠在一起：

1. 阶段固定。plan、confirm_outline、write、review 每个请求必经，没有跳过条件。
2. 深度前置。章数在看到任何证据之前由策划一次性定死，而且提示词给的是固定区间。
3. agent 的自然停止被关掉了。`create_agent` 的 ReAct 循环本来就是"有工具就调、能答了就停"（R1 探针验证过它会自己停），但外层每章都要求它凑 4～8 条论断、把每章当成独立任务，等于把这个能力关掉了。

Sean 的两条批评都指向这里："为了展示卡片而设计"和"上来就一个大工程"。

## 3.1 交代：哪些是 Claude 自己定的

下面这些都是 Claude 在 R1～R4 实现时自己做的决定，Sean 没有提过这些要求，讨论时不要当成需求：

- 策划固定拟 3～4 章；每章要求产出 4～8 条论断。
- 大纲确认和终审每个请求必经；范围确认原先无条件逐项弹卡。
- 每章的上限：3 次搜索、3 次读原文、20 次模型调用（从 14 提上来的）；整线程提问上限 6 次。
- 每章独立跑一个 agent、串行执行。
- 检查放在写报告之后、只展示不回补。

Sean 实际提过的只有：把 HITL 环节体现出来；每轮提问最多 3 次；统一用豆包；不要面面俱到；先把一个场景处理好。Sean 在 10-27 看到效果后的批评是"为了展示卡片而设计"和"上来就一个大工程"，Claude 认同这两条，根因见第 3 节。

## 4. 几种可能的方向

### 方向 A：保留固定阶段，给每个阶段加跳过条件

intake 多判断一个复杂度（简单事实题 / 单主题 / 多维度），plan 按复杂度定 1～4 章，简单题跳过大纲卡和终审卡，直接出"一句结论 + 关键数据表 + 要点 + 来源"。

- 好处：改动小，现有测试和接口基本不动，可预测。
- 问题：深浅由一个看不到证据的分类器决定，判错就是答浅了还不自知（Sean 的担心）；每遇到一类问题就要加一个分支，骨架越补越厚；本质上还是在提示词里兜。

### 方向 B：外层图做薄，一个 agent 对整个问题干活

一个 `create_agent` 循环对整个问题负责，搜索、读原文、提问是它的工具；"拆大纲"也变成一个它需要时才调的工具（调了才进入分章模式），大纲确认、终审这些 HITL 节点由 agent 触发时才出现（interrupt 在工具里发）。天气题就是循环跑几步停下；海报调研题是同一个循环里它自己决定拆章、逐章查。

- 好处：深浅是跑出来的，不是分类出来的；一个机制不是两条路；天然利用 agent 的停止判断。
- 问题：图重做一遍，不是小改；HITL 点变成不可预测的（测试、前端都要适应"任何时候可能弹任何卡"）；"agent 会不会在该拆章的时候不拆"同样是模型判断，2.3 说明真实模型目前不爱用可选工具；每章独立消息历史（现在的隔离）会丢，长问题的上下文会膨胀。

### 方向 C：B 的保守版，先查后定

保留阶段，但把"定章数"挪到第一次搜索之后：先对整个问题搜一次，拿着结果让策划决定是直接答还是拆成几章（拆了才走后面的流程），直接答的话就一步成文。

- 好处：深浅判断至少看过证据；改动介于 A 和 B 之间；固定阶段仍可预测。
- 问题：仍然是一次性判断，只是晚了一步；还是两条路。

无论哪个方向，下面这些应该留在代码里而不是交给提示词：论断必须有来源否则丢弃；排除来源要撤回依赖它的论断；时间范围检查；导出只带采纳的来源。

## 5. 想和 Codex 一起讨论的问题

1. A / B / C 选哪个，或者有没有第四种。判断标准建议是：天气题能不能在一分钟内一步答完，海报调研题能不能不靠人提醒自然走到多章；以及改完之后再遇到新类型的问题时，是不是不用再加分支。
2. 如果走 B，HITL 节点怎么由 agent 触发比较稳：interrupt 放在工具里（langgraph 支持，但中间件和 create_agent 的组合要验证）、还是 agent 返回一个"我要确认大纲"的结构化结果让外层图去中断？
3. "复杂的问题被做浅了"怎么防，而且不能靠用户看流程来纠正（用户只看答案）。候选：成文前的覆盖检查（问题的每个部分是否有有来源的事实）由代码强制回补；拿不准宁可深。有没有更靠谱的？
4. 真实模型不调 ask_user 这件事，要不要先定位（是提示词、是工具描述、还是豆包的工具调用偏好），因为方向 B 依赖模型会主动用可选工具。
5. 每章消息历史隔离现在是靠 create_agent 不传 checkpointer 得到的。走 B 以后怎么控制上下文长度。
6. 海报场景暂不动（Sean 的要求：先把一个场景处理好，再平滑迁移），但选方向时要考虑海报将来能不能套同一个骨架。

## 6. 约束（Sean 定的，讨论时当前提）

- 这是 PoC，核心是把 HITL 体现出来，但 HITL 的价值在于模型拿不准时拿到更清晰的指令，不在于卡片出现的次数。原话里有的不要拿回去确认；需求清楚就直接干。
- 不要面面俱到。流程深度要按问题伸缩，先做最薄的能跑通的版本。
- 一次只处理好一个场景，验证稳了再平滑迁到其他场景。
- 模型统一用豆包，不追求模型输出完美。
