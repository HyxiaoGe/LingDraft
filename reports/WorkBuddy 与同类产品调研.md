# 确认点收敛到大纲，溯源与可编辑决定胜负

截至 2026 年 10 月，WorkBuddy 与同类产品在"从需求到交付物"流程上已经收敛出一个共同骨架：**生成前默认不问或只问一轮缺失信息、把唯一的硬确认点放在大纲/计划、生成后用"选区 + 指令"做局部修改、以原生可编辑文件交付**。WorkBuddy 2026-09-14 升级后的 PPT 流程（只在信息缺失时追问受众/场景/目标、点选元素下指令、改一页不影响其他页、输出标准 .pptx）正是这个骨架在国内的样板；但它的海报路径没有任何澄清步骤、HTML 海报的排版要改 3–4 轮、深度研究只是一个技能包而非产品模块，而且 Sean 在"黑色星期五海报"案例中观察到的"先问视觉风格"很可能是模型临时调用 AskUserQuestion 选择器的结果，而不是固定流程。对 LingDraft 的直接含义是：三个场景"问什么"已有明确先例可抄，真正没有任何产品做好的是三件事——**价格/日期等关键事实的结构化与校验（不能交给像素渲染）、报告中事实与推断的显式分层并随内容迁移进 PPT 备注和海报脚注、以及"已确认内容不被重生成破坏"的状态机**。架构上，海报、PPT、调研三条线的公开证据都指向同一模式："规划层输出结构化 JSON → 渲染层出像素或 OOXML → 渲染后自动校验"，与 LangGraph 的 `interrupt` / checkpoint 天然契合；需要预先规避的是 interrupt 的节点重跑与审批伪造、以及中文信源（公众号无官方 API）的硬约束。

## WorkBuddy 的 PPT 流程最成熟，海报与调研路径仍然粗糙

WorkBuddy 是腾讯云 CodeBuddy 团队出品的桌面端办公 Agent，**2026-03-09 正式发布**（1 月内部试用、2 月外部内测），并非 2025 年产品；上线当天因流量超预期出现登录不稳并公开致歉 ([Baidu Baike (en)](https://baike.baidu.com/en/item/WorkBuddy/1915792))。TechNode 将其定义为"OpenClaw-like desktop AI agent"，本地安装免部署，兼容 OpenClaw skills，可切换混元 / DeepSeek / GLM / Kimi / MiniMax ([TechNode 2026-03-09](https://technode.com/2026/03/09/tencent-launches-openclaw-like-workplace-ai-agent-workbuddy/))。它有 Ask / Plan / Craft 三种模式：Craft 直接执行并改文件，Plan 先出执行计划待确认，Ask 只读不写 ([奇连 AI](https://iqilian.com/learn/workbuddy-sanzhong-gongzuo-moshi/))。花旗研报引用腾讯管理层口径称跨平台 MAU 2,000 万、DAU 超 1,300 万，属厂商数据 ([itiger/Citi](https://www.itiger.com/news/1125565486))。

生成前的澄清行为在 WorkBuddy 里是"按入口分化"的。客户端存在"问答选择器"（AskUserQuestion）卡片，4.24.0 起支持选项之外的自定义输入，5.2.6 修复过"AskUserQuestion 等待状态被流式帧覆盖"的 bug ([官方 Changelog](https://www.codebuddy.cn/docs/workbuddy/Changelog))——这在形态上正是 Sean 观察到的"推荐选项 + 自由补充"。但官方 Ardot 设计创意文档明确写着风格靠"设计风格模板"下拉选择，**"未选择时 AI 会根据你的描述自动匹配风格"**，全文未提先追问 ([官方 Design-Idea 文档](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Design-Idea))；企业版的小红书海报实测中也没有出现任何澄清提问或风格菜单，系统直接把任务拆为设计、文案、违禁词规避、导出四步执行 ([腾讯云开发者社区 2026-07-21](https://cloud.tencent.com/developer/article/2713388))。把这两组证据放在一起，合理推断是：海报路径的"先问风格"由模型在 Craft 模式下自行决定是否调用选择器，同一任务换一次运行可能就不问了。只有 PPT 功能在 2026-09-14 的升级里把追问写进了流程——只给主题和页数时先问汇报对象、场景、目标，再搭"问题—论证—结论—落地"主线，并且官方强调"**只在信息缺失时追问必要问题，用户已经说明的不再重复问**" ([AIbase 2026-09-14](https://news.aibase.com/zh/news/31036))。这条原则与 LingDraft 简报里"只问返工成本高的信息、不重复问已表达内容"完全一致，可以直接作为 PPT 场景的对标基线。

生成后的修改分三层。Ardot 画布支持"智能框选 + 对话"做局部精准调整、"纯语言指挥"做全局调整、"粘贴参考"借鉴网页或参考图风格，每轮修改后 Agent 说明本轮改动，并可一键进入 Ardot 完整编辑器（拖拽、像素级对齐、图层管理），编辑器中的改动实时回流 WorkBuddy ([官方 Design-Idea 文档](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Design-Idea))。PPT 升级后可点选或框选标题、文本框、图片、图表再下指令（"这一页拆成两页""表格转图表""这页风格对齐上一页"），官方称之为"人机双写"并承诺"改一页不影响其他页" ([AIbase](https://www.aibase.com/zh/news/31036))；5.4.0 加入了本地 PPT AI 编辑的撤销/重做 ([官方 Changelog](https://www.codebuddy.cn/docs/workbuddy/Changelog))。相比之下，通用 Agent 直接写 HTML 的海报路径只是"改源码再刷新预览"：标题放大、卡片改两列这类请求可以即时生效，但内容溢出修了 3–4 轮，作者建议"一次说清所有要求、批量提修改、约 15 轮后开新对话" ([腾讯云开发者社区 2026-07-21](https://cloud.tencent.com/developer/article/2713388))。

交付物方面，PPT 输出标准 .pptx，可在 PowerPoint / WPS 继续编辑并导入腾讯文档协作 ([AIbase](https://www.aibase.com/zh/news/31036))；Ardot 设计稿可导出 PNG / SVG / PDF 并支持切图标注，PPT 可导 PPTX / PDF，设计稿存储在云端 ([官方 Design-Idea 文档](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Design-Idea))；HTML 海报则产出 1080×1440 的 HTML 加一份 .txt 文案文件，导出 PNG 必须依赖本机 Chrome headless 截图，且重复导出会读到缓存旧图 ([腾讯云开发者社区 2026-07-21](https://cloud.tencent.com/developer/article/2713388))。也就是说，WorkBuddy 的海报其实有两条交互差异极大的路径：Ardot 路径给可编辑的分层稿，通用 Agent 路径给不可分层的 HTML/PNG。深度研究在官网被宣传为"自动检索多渠道公开资料与本地参考文档，输出结构化报告、竞品矩阵，支持 .md / .pptx / .docx，15 分钟交付" ([codebuddy.cn/work](https://www.codebuddy.cn/work/))，但官方 Changelog 没有专门条目，社区依赖第三方 GitHub 技能包实现"拆问题、判来源、带引用整理"，研究 UX（澄清、计划、引用形式）没有任何官方说明或独立实测。

已知弱点集中在严谨性与长内容。钛媒体的企业微信实测中，周报日期被写成早一年的 2025 年 10 月，模型先否认后承认"幻觉"，次日复测仍错，直到显式写明"2026年10月16日"才修复 ([钛媒体 via 搜狐 2026-10-20](https://www.sohu.com/a/1090078197_122014422))；V2EX 用户反映 30 页以上带严格模板的 PPT 从未成功、50 页以上文档出胡话，但"短的营销海报和文章效果不错" ([V2EX](https://www.v2ex.com/t/1232713))；流式切断 UTF-8 导致的中文乱码在 5.3.6 / 5.3.7 修复，**5.9.1（2026-10-22）才"优化 PPT 生成的素材核对，减少内容与配图不符"** ([官方 Changelog](https://www.codebuddy.cn/docs/workbuddy/Changelog))。奇连指南指出 Craft 模式会"过度改动"——删掉想保留的内容、破坏格式、跑偏 ([奇连 AI](https://iqilian.com/learn/workbuddy-sanzhong-gongzuo-moshi/))，这正是"保留已确认内容"没有被做成显式机制的后果。定价上个人版 2026-07-01 起分体验版免费 500 积分、标准版 99 元、高级版 199 元、旗舰版 999 元每月 ([官方 Pricing](https://www.workbuddy.cn/docs/workbuddy/Pricing))，一张含多轮修改的海报约消耗 200–300 积分 ([腾讯云开发者社区 2026-07-21](https://cloud.tencent.com/developer/article/2713388))。

## 生成前：主流产品默认不问，只问一轮缺失信息，大纲是唯一硬确认点

四类产品在"问不问、问几个、怎么问"上的答案惊人一致。通用办公 Agent 里，Manus Plan Mode 的官方表述是"**If the request lacks context, Manus asks questions first. If the path is clear, it generates the plan right away**"，计划是含 goals / steps / constraints 的 Markdown 文档，Plan Mode 为手动开启，FAQ 明确"Your quick tasks stay quick" ([Manus: Introducing Plan Mode](https://www.manus.im/blog/manus-plan-mode))。Microsoft 365 Copilot Researcher "might ask follow-up questions"，但用户回一句 "Go ahead" 即可跳过 ([Microsoft Support](https://support.microsoft.com/topic/e63ab760-f3de-4c47-ae87-dad601b0e9c4))。Notion 把"问"做成三档全局设置：Always ask / Review for me（默认，Agent 自审只在可能不安全时暂停）/ Skip all approvals，发送前可切换 ([Notion Help](https://www.notion.com/help/choose-how-notion-agent-asks-for-your-approval))。Lovable Plan mode "often asks clarifying questions first"，但只有在有清晰方案时才写计划 ([Lovable Plan mode](https://docs.lovable.dev/features/plan-mode))。

深度研究类产品把这一步做成了"澄清"或"可编辑计划"二选一。OpenAI 在 Chat 中先生成一份可审阅修改的研究计划并允许过滤网站、补充信源，在 Work / Codex 中则改为先提澄清问题 ([OpenAI Help Center（搜索摘要）](https://help.openai.com/en/articles/10500283-deep-research-in-chatgpt))；Gemini 应用端展示多点研究计划供编辑，API 端用 `collaborative_planning` 开关先返回计划、用 `previous_interaction_id` 来回修改、再设为 False 批准启动 ([gemini.google](https://gemini.google/overview/deep-research/); [ai.google.dev](https://ai.google.dev/gemini-api/docs/deep-research))；Kimi 提交后"提出一轮澄清问题"，可点"做个全面的研究"跳过，并提醒"长而不清晰的输入会带偏方向" ([kimi.com 帮助中心](https://www.kimi.com/zh-cn/help/deep-research/deep-research-overview))；阿里云百炼的 Qwen-Deep-Research API 干脆把它固化为两步调用——第一次返回澄清问题，第二次传入用户回答启动研究 ([help.aliyun.com](https://help.aliyun.com/en/model-studio/qwen-deep-research-api))。反面是 Perplexity：收到首条查询即进入深度研究、没有澄清环节，用户评价认为这迫使自己写极详细的 prompt ([uzyn.com](https://uzyn.com/2025/thoughts-on-perplexity-deep-research-after-24-hours/))。

PPT 类产品则把确认点压在大纲上。Gemini in Google Slides（2026-06-30）的流程是输入 prompt → 附 Drive 文件作内容依据 → 附现有 deck 作风格参考 → 回答 Gemini 关于语气/风格/内容/受众的追问 → **审阅并编辑/批准大纲** → 生成 ([Google Workspace Updates](https://workspaceupdates.googleblog.com/2026/06/create-fully-native-and-editable-presentations-with-Gemini-in-Google-Slides.html))；Copilot in PowerPoint 可能追问受众、长度、模板方向、配图，可回答或跳过 ([Microsoft Support](https://support.microsoft.com/en-us/topic/create-a-presentation-from-existing-files-beb15deb-3241-4711-a480-9cbd8dc4d755))；Skywork 用结构化"澄清卡片"和"待办清单"在生成前确认 ([ai-bot.cn Skywork](https://ai-bot.cn/skywork/))；秘塔 PPT 固定三问——知识掌握程度、画面风格、讲解风格 ([量子位 2025-12-09](https://www.qbitai.com/2025/12/359845.html))；WPS 灵犀是"一句话生成大纲 → 确认后生成 PPT，支持多轮改大纲、换模板" ([新浪：WPS 灵犀 3.0 实测](https://k.sina.com.cn/article_7857141524_1d452771401902kwa4.html))。跳过大纲的产品被评测点名：Manus Slides 自动起草大纲、**不提供审阅步骤**，要改方向只能等或停止 ([Plus AI: Manus review](https://plusai.com/blog/manus-ai-slide-generator-review))；NotebookLM 的大纲共创仅对 Google AI Ultra 订阅者开放，且审阅时必须一次性给完反馈，之后不可再改 ([Google NotebookLM Help](https://support.google.com/notebooklm/answer/16757456))。Google 把大纲共创做成付费特权，本身就说明它被视为高价值交互。

海报类产品几乎没有对话式澄清，"风格"被做成模板选择而不是提问。Canva AI 描述海报后约 5 秒给出 3 个模板选项 ([CSDN 2026-05-19（推广文，仅取流程）](https://blog.csdn.net/2401_89926894/article/details/161106579))；Adobe Express 的 Generate Template 从结果中选一个进入 "Edit template"，可 "Generate more results" 或对某个结果 "See variations"，风格词直接写在提示里 ([Adobe Help](https://helpx.adobe.com/express/web/create-with-templates/text-to-template.html))；国内电商 Agent 的"澄清"是结构化输入：京点点 Oxygen Vision 输入京东 SKU 后自动读取商品名/卖点/规格，再选目标平台、销售区域、语言，匹配平台图片规范与文化禁忌后分钟级出 10 张套图 ([京东云开发者 2026-04-13](https://developer.jdcloud.com/article/4484))；堆友 Agent 输入一句话卖点 + 商品实拍图或产品 Excel 批量 ([umaax 堆友实测](https://umaax.com/duiyouagentshiceaiyijuhuashengchengshangyejidianshangshejiha/))。这意味着海报场景的"缺失信息"是明确可枚举的——渠道尺寸、商品图、品牌素材、关键事实字段、风格——更适合表单式一次收齐，而不是多轮问答。

"怎么问"已有标准 schema 可借。MCP elicitation（2026-07-28 版）的 form mode 限定为扁平对象 + 原始类型，enum 支持 `oneOf` + `title` 单选、`anyOf` 多选、`default` 预填，响应三态 `accept / decline / cancel`，客户端"MUST allow users to review and modify their responses before sending" ([MCP Elicitation spec](https://modelcontextprotocol.io/specification/latest/client/elicitation))；LangGraph `interrupt(value, response_schema=...)`（`langgraph>=1.2.12`）可给 interrupt 附 Pydantic schema，resume 值校验失败抛 `ValidationError` 并可在同一 thread 重发 ([LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md))。中文社区的设计共识是"每次只问 1–2 个关键信息，给出选项，不要让用户输入开放式答案" ([CSDN](https://blog.csdn.net/TSG415545321/article/details/162242182))，以及两种反面——"要么不问、直接瞎猜，要么问太多、把用户当傻子" ([腾讯云社区](https://cloud.tencent.com/developer/article/2553570))；没有任何厂商公开"问题数量上限"的书面规范，1–2 个/轮是经验值而非标准。

对 LingDraft 的结论：澄清应由"每个场景的高返工成本字段清单是否缺失"驱动，而不是由模型临场判断。PPT 场景的清单是受众/场景/目标 + 页数 + 模板（WorkBuddy、Gemini、Copilot 三家一致）；海报是渠道尺寸集 + 商品图/品牌素材 + 价格/日期/规则等关键事实 + 风格（京点点、堆友、Ardot 的结构化输入）；调研是范围 + 信源偏好（域名白名单、上传资料、中英文比例）+ 交付形式（OpenAI 的过滤网站与补充信源、Gemini 的可编辑计划）。表单用 MCP elicitation 的扁平 schema 渲染，带推荐默认值和"直接开始"跳过键；大纲/计划卡作为唯一硬确认点，支持 Lovable 式"选中一段点 Comment 只改那一段"与 undo/redo ([Lovable Plan mode](https://docs.lovable.dev/features/plan-mode))；再加一个 Notion 式的"每步确认 / 关键处确认 / 不打扰"用户设置，而不是把提问频率写死在 prompt 里。

## 生成后："选区 + 指令"已成共识，但"保留已确认内容"没有人做成显式机制

2026 年所有头部产品的局部修改都收敛到同一个手势：选中一块，说一句话。Claude 2026-06-12 的 release note 写的是 "Highlight the part you want changed, type the change" ([Claude Release notes](https://support.claude.com/en/articles/12138966-release-notes))；Gemini Canvas 用 "Select & ask" 选中文本/区段后输入 prompt，顶部可用 Previous Version / Next Version 穿梭版本，但 Gemini Enterprise 的 Canvas "each update generates a completely new Canvas artifact"、不保留版本 ([Gemini Apps Help](https://support.google.com/gemini/answer/16047321?hl=en&co=GENIE.Platform%3DDesktop); [Google Cloud: Gemini Enterprise Canvas](https://docs.cloud.google.com/gemini/enterprise/docs/assistant-canvas))；WorkBuddy V5.3.5 的"人机双写"把完整文档编辑器放在聊天框旁，选中一段下指令就地改写 ([钛媒体 2026-08-02](https://www.tmtpost.com/8088161.html))。

PPT 场景把这个手势细化到了页与元素，差异在于版本与接受粒度。Gamma 的 Agent 模式可指定整份/单页/单元素，修改后给 Original / Modified 对比，但一次请求的改动只能**整体接受或回退、不能逐条接受** ([Gamma Help](https://help.gamma.app/en/articles/8033284-can-i-edit-my-content-using-ai))；Kimi Slides 支持在页面或元素上加批注定点修改，**每轮 AI 修改自动存为独立版本**可对比回退 ([kimi.com features/slides](https://www.kimi.com/zh-cn/features/slides))；Claude for PowerPoint 强调 "pinpoint edits to specific slides without regenerating entire decks"，并读取 slide master、版式、字体、配色生成 ([claude.com docs](https://claude.com/docs/office-agents/powerpoint))；WPS AI 提供"单页重新生成" ([36氪 2026-09-07](https://eu.36kr.com/zh/p/3973165784740354))。反例同样清楚：NotebookLM 的 Revise 把单页指令汇总为 Pending Changes 后"Generate revised deck"，**每次修订生成全新 deck 且受配额限制** ([Google NotebookLM Help](https://support.google.com/notebooklm/answer/16757456))；Genspark 被评测认为对 "repeated micro-edits" 不划算，信用点随修改轮次快速消耗，"revision consistency" 是公开抱怨点 ([lindy: Genspark review](https://www.lindy.ai/blog/genspark-review))。

海报场景的局部修改能力由"有没有图层"决定。走模板/图层路线的产品修改稳定：创客贴 AI 改图把标题"山野寻味"改为"山野特菌"而排版样式不变 ([知乎 创客贴 AI 改图](https://zhuanlan.zhihu.com/p/2004844250890781190))；Ardot 的智能框选与完整编辑器前文已述。走图像模型路线的产品普遍"改不了小东西"：独立测试显示 gpt-image-1.5 的遮罩编辑会重绘整图，紧遮罩外仍有 **7–9% 像素可见变化** ([understandingdata](https://understandingdata.com/ai-engineering-visualised/image-editing-masks/))；Recraft V4.1 仍不能只动一个对象或只改一块颜色 ([therundown](https://www.therundown.ai/tools/recraft-v4))；Lovart Edit Elements 拆层时小字、密集图标易误判，描边/渐变字效可能丢失，测试中一张中文 banner 的字体被换掉 ([agiyes](https://www.agiyes.com/ainews/lovart-edit-elements/))；Ideogram Layerize 官方自述可能漏字且文字下方背景会被重绘，提醒用户"检查小字、日期和页脚" ([Ideogram: Text Layers](https://ideogram.ai/features/text-layers/))。2026 年的进展是 Seedream 5.0 Pro（2026-07-08）可用文字指令把一张海报拆成 10+ 独立图层、自动补全被遮挡背景、点选/套索/涂鸦转为局部编辑指令，但自述"更细粒度文字渲染仍有提升空间" ([ByteDance Seed Blog](https://seed.bytedance.com/en/blog/beyond-generation-it-understands-design-introducing-seedream-5-0-pro))；Qwen-Image-Edit-2511 则可在保持原字体/字号/风格的前提下增删改海报文字 ([Replicate](https://replicate.com/qwen/qwen-image-edit-2511))。

调研场景是三类里局部修改最弱的。没有任何主流产品支持"只重写某一节、其余保持不变"的节级再生成；OpenAI 只允许运行中中断并调整研究重点与信源 ([OpenAI Help（搜索摘要）](https://help.openai.com/en/articles/10500283-deep-research))，Gemini API 允许完成后用 `previous_interaction_id` 追问而不重跑 ([ai.google.dev](https://ai.google.dev/gemini-api/docs/deep-research))，Gemini Canvas 的编辑是文档级编辑而非研究级再跑。这是 LingDraft 调研场景可以直接超越的空白。

下表压缩了各产品在修改粒度、版本、接受粒度上的差异：

| 产品 | 修改入口 | 粒度 | 版本/回退 | 接受粒度 | 评价 |
|---|---|---|---|---|---|
| WorkBuddy PPT | 点选/框选元素 + 指令 | 页/元素 | 撤销/重做（5.4.0） | 未说明 | 官方称改一页不影响其他页，无独立评测 |
| WorkBuddy Ardot | 智能框选 + 对话；完整编辑器 | 元素 | 每轮说明改动 | 未说明 | 实测文章 403，质量未验证 |
| Gamma Agent | 选元素 / 单页 / 整份 | 元素 | Original/Modified 对比 | 整体接受或回退 | 不能逐条接受 |
| Kimi Slides | 批注定点 | 元素 | 每轮自动存版本 | 未说明 | 版本粒度最明确 |
| Claude for PowerPoint | 选中单页指令 | 页 | 宿主编辑器 | 宿主编辑器 | 读取 master 生成 |
| NotebookLM | 单页 Revise | 页 | 每次全新 deck | 全量 | 反例：修订受配额限制 |
| Lovable Plan | 选段 Comment | 段 | undo/redo，旧版只读 | 段 | 计划层局部重生成范式 |

框架层给出了"编辑而非重做"的工具：LangChain `HumanInTheLoopMiddleware` 的 `edit` 决策直接改工具参数（`edited_action`），文档提醒 "keep changes small"，大改会让模型重新评估甚至重跑工具 ([LangChain Human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop.md))；LangGraph `update_state(config, values, as_node=...)` 创建新 checkpoint 而非改旧的，用历史 `checkpoint_id` 重新 invoke 可从该点分叉 ([LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers.md))。没有任何产品公开"锁定已确认页"的 UI 或"局部重生成时如何保证与已确认页风格一致"的技术说明，实际做法只有三种：选区级指令让模型只产出选区替换、产物可直接手工编辑（手工编辑即隐式确认）、版本穿梭兜底。LingDraft 应把它做成显式状态机：每页/每个元素/每个章节维护 `status: draft | confirmed | user_edited` 与 `version`，重生成节点只处理 `draft` 项，用户手工编辑通过 `update_state(as_node=...)` 写回 checkpoint 形成分叉点，修改结果以 diff/patch 而非整份产物返回前端（AG-UI 的 `StateDelta` 即 RFC 6902 JSON Patch），并在 UI 上明示"本次只改了 X"。按 AI 轮次存版本（Kimi）叠加逐条接受（Gamma 没做到）是可超越的点。

## 可编辑性与可追溯性：原生文件与结构化事实是硬门槛，事实/推断分层无人做到

PPT 的"可编辑"有三个可验收的硬指标：文本是否按段落合并为一个文本框、表格/图表是否为原生对象、是否带 slide master。Gamma 官方导出说明承认 PPTX **不包含 slide master**（PowerPoint 母版为空）、斜体为合成斜体、渐变标题可能导出为单色 ([Gamma Help: export](https://help.gamma.app/en/articles/8022861-what-s-the-easiest-way-to-export-my-gamma))，用户反馈板上"每个 bullet 甚至每个换行各自一个文本框"的投诉促使 Gamma 部署了合并修复 ([ideas.gamma.app](https://ideas.gamma.app/ideas/p/text-exports-to-powerpoint-as-line-by-line-instead-of-one-big-text-box))；Genspark 被竞品评测描述为"HTML 演示文稿而非原生 PPTX" ([Plus AI: Genspark review](https://plusai.com/blog/in-depth-genspark-review))；NotebookLM 的幻灯片由 Nano Banana Pro 生成为静态图片，不能编辑文本框，用户还报告纠错后错误仍在、**伪造来源引用** ([eesel.ai](https://www.eesel.ai/blog/notebooklm-slide-deck-feature))。方向性信号是 Manus 的管线切换：旧管线"web 格式生成、导出时转 .pptx，会有格式问题"，新管线"从第一页起就写原生 .pptx"，图表背后是可点击编辑的数据表、表格是真实单元格 ([Manus blog](https://manus.im/blog/manus-ppt-slides))；Anthropic 官方 pptx skill 同样是新建用 pptxgenjs、编辑走 OOXML 直改 `ppt/slides/slideN.xml`、图表用 `addChart()` 保持原生，再用 LibreOffice headless 转 PDF + `pdftoppm` 逐页目检，并把"文字溢出"列为最常见缺陷 ([anthropics/skills pptx SKILL.md](https://github.com/anthropics/skills/blob/main/skills/pptx/SKILL.md))。头部团队正在从"HTML 再转"退回"直接产出 OOXML 并用渲染做 QA"。

数据保真是 PPT 评测 2026 年的新焦点。一份国内六款横评（3000 字 Word → 20 页，32 个数据点）显示只有即触 AI PPT 的"保持原文"模式跳过 LLM 改写、32 个数据/单位/小数全部保留；aippt 把精确数字改成约数、具体百分比改成"显著下降"，Gamma 润色措辞并取约数，Beautiful.ai 改写文字和数字——该文页脚自称"模拟测试"且推荐即触，数字需谨慎，但"多数工具改写用户数字"的定性结论与其他评测一致 ([CSDN/gitcode 2026-06-04](https://gitcode.csdn.net/6a2132d1662f9a54cb79820f.html))。更早的四款国产实测中（WPS AI、Kimi、百度文库、讯飞智文），统一 prompt 要求含图表，**四款均未生成图表**，百度文库还在《傲慢与偏见》deck 里用了《小妇人》剧照 ([澎湃/科技新知 2024-08-28](https://www.thepaper.cn/newsDetail_forward_28535491))。"原文模式/数字锁定"是被评测直接奖励、而头部大厂尚未普遍提供的功能。

海报的可编辑性由生成路线决定，而"促销文字"的准确性由文字是否走文字层决定。全球工具已分化为两条路线：模板/图层优先（Canva Magic Design、Adobe Express Generate Template、Figma Buzz、Kittl）从一开始就输出文字为文字层的可编辑设计；图像模型优先（Ideogram、Recraft、Nano Banana Pro、GPT Image、Lovart）输出位图，再靠"拆层"补课。Canva Magic Layers（2026-03-11 公测）把平面图转为多图层设计、文字恢复为可编辑文本框，属于 Canva Design Model"从一开始就生成可编辑设计"的能力 ([Canva Newsroom](https://www.canva.com/newsroom/news/magic-layers/))；**Canva Craft（2026-10-22）**更进一步采用两阶段架构——"图像规划模型"先解析提示写出版式、文字、层级的构图计划，再由独立"渲染模型"出图，训练于 Canva 内容库数百万人工模板，并以 "JSON boundary boxing" 转为可编辑图层 ([Canva Newsroom: Canva Craft](https://www.canva.com/newsroom/news/canva-craft/); [TechCrunch 2026-10-22](https://techcrunch.com/2026/10/22/canva-releases-its-first-image-generation-model/))。国内模板型产品的中文准确度优势同样来自"文字是文字层"：稿定 AI 可导出分层 PSD、"智能图文排版"调整图文层级 ([搜狐 2026-05-28](https://www.sohu.com/a/1028558781_122725336))；美图设计室的价签、折扣标签、标题为文字层 + 矢量装饰，点击文本块即可改 ([搜狐 2026-05-28](https://www.sohu.com/a/1028558781_122725336))。而模型型产品在促销字上仍会错：推广性质的横评中即梦"全场5折"出现字形错误 ([AtomGit 2026-05-14（推广文）](https://gitcode.csdn.net/6a05874a54b52172bc742ec4.html))，Microsoft Designer 的评测建议"先生成不含关键文案的视觉，再把最终文案作为可编辑画布文字加上" ([toolsforhumans](https://www.toolsforhumans.ai/ai-tools/microsoft-designer))，Google 对 Nano Banana Pro 的官方提示技巧也是"先和模型对话生成文案，再要求把该文案放进图"并自认"文字渲染、事实准确性仍需改进" ([Google Prompting Tips](https://blog.google/products-and-platforms/products/gemini/prompting-tips-nano-banana-pro/))。合规层面的后果是真实的：央广网 2026-01-16 报道商家未显著提示 AI 生成主图若构成广告且违反广告法可罚 20–100 万元 ([央广网](https://www.cnr.cn/mspd/zhsh/20260116/t20260116_527494911.shtml))，江苏市监 618 提示点名"AI 造假、虚假促销、'全年最低价'绝对化用语、虚标原价" ([新华报业](https://www.xhby.net/content/s6a3395d9e4b0baeb0111ce5f.html))。对 LingDraft 而言，价格/日期/活动规则必须作为结构化字段走文字层并做合规词校验，图像模型只渲染氛围性大字或装饰字，必要的像素中文（艺术字标题）用 Seedream 5.0 Pro / 混元 3.0 / Qwen-Image 并以 OCR 回读校验。

调研的可追溯性，行业默认 UI 是"正文内联引用 + 点击跳转高亮原文"，但没有任何产品在报告中显式标注"这是推断"或给出句级置信度。Kimi 的引用内嵌正文、点击跳转并高亮原文，平均每份报告约 26 个信源、超一万字，每任务发现约 206 个 URL 只保留前 3.2% 高质量内容 ([kimi.com 帮助中心](https://www.kimi.com/zh-cn/help/deep-research/deep-research-overview))；天工的文档/PPT/网页带溯源标签，**正文可链接到来源的具体段落、图片可链接到知识源**，是目前最细粒度的引用模型 ([36氪转载新智元 2025-05-22](https://www.36kr.com/p/3303246919228167))；秘塔在"白布"上实时生成研究路径图，每个子问题结论用颜色标注——绿=已得出结论、紫=仍在完善、红=信息缺失——并且每个知识点可点击到原文 ([量子位 2025-07-15](https://www.qbitai.com/2025/07/309591.html))；OpenAI 完成后提供 "sources used" 区块与 "activity history" ([OpenAI Help（搜索摘要）](https://help.openai.com/en/articles/10500283-deep-research))。学术工具是唯一把"证据一致性"可视化的例子：Scite 展示后续论文对某结论的"支持/反驳"，Consensus Meter 展示研究分歧 ([paperguide.ai](https://paperguide.ai/blog/elicit-vs-consensus/))。

引用幻觉有量化证据，而且与引用数量呈反向关系。跨 10 个模型/Agent 在 DRBench 上，**3–13% 的引用 URL 完全虚构、5–18% 无法解析**，深度研究 Agent 每问引用更多但 URL 幻觉率更高 ([arXiv 2604.03173](https://arxiv.org/pdf/2604.03173))；ReportBench 人工审计区分了"陈述幻觉"（来源并不支持该论断）与"引用幻觉"（参考文献捏造），例子包括 OpenAI Deep Research 把作者归给不在作者列表的人 ([arXiv 2508.15804](https://arxiv.org/pdf/2508.15804))；DeepResearch Bench 显示 Gemini-2.5-Pro Deep Research 平均 111.21 条有效引用显著领先，但引用准确率相比 Perplexity 有明显差距 ([arXiv 2506.11763](https://arxiv.org/pdf/2506.11763))。Simon Willison 的提醒更重要：核对引用能抓到大部分幻觉，但"遗漏"更难发现，带标题和引用的"报告体"会制造误导性的专业感 ([simonwillison.net](https://simonwillison.net/b/8511))。工程上的应对是把引用绑定前移到研究阶段：Anthropic 的系统在研究结束后由独立的 CitationAgent 把每条论断对应到来源，子代理 prompt 内置"信源质量启发式"以避免偏好 SEO 内容农场 ([anthropic.com/engineering](https://www.anthropic.com/engineering/built-multi-agent-research-system))；LangChain Open Deep Research 让子代理结束时写出"带引用的详细答案"再清洗后交回 supervisor ([langchain.com/blog](https://www.langchain.com/blog/open-deep-research))。

"研究 → PPT/海报"的引用迁移有两种模式。天工把研究产物直接作为带溯源的 PPT，NotebookLM 让 Deep Research 的报告与全部来源进入 notebook 后再生成 Slide Deck，并支持上传品牌规范作为 source 统一风格 ([christopherspenn.com 2026-02](https://www.christopherspenn.com/2026/02/notebooklms-game-changing-upgrade-create-stunning-infographics-slides-deep-research-in-one-powerful-ai-tool/))；Genspark / Manus / Perplexity Labs 则由 Agent 一次性生成 deck，引用基本丢失。没有任何产品公开说明把引用保留进 PPT 讲者备注或幻灯片脚注，也没有产品级的"研究 → 营销文案"流程。LingDraft 应在写作节点强制结构化输出——每条论断带 `kind: fact | inference`、`sources[]`、`quote`、`confidence`——用秘塔式颜色与 Scite 式支持/反驳标记呈现，对每个 URL 做可达性与引文包含性校验，把"少而准"设为默认，并让 PPT 备注与海报脚注自动携带来源。这是三个场景里差异化最明确、且全部竞品都空着的位置。

## 架构：公开证据指向"规划 JSON → 渲染 → 自动校验"，LangGraph 落地有先例也有陷阱

深度研究的参考架构在 2026 年已经收敛。Anthropic 的多代理系统采用 orchestrator-worker：Lead 制定策略并并行派发 3–5 个子代理，各自 3+ 工具并行调用，复杂查询总耗时降低最多 90%，但多代理约消耗 **15× 聊天 token**；努力度分级为简单事实 1 代理 3–10 次工具调用、直接比较 2–4 子代理各 10–15 次、复杂研究 10+ 子代理；失败模式包括过度派生 50 个子代理、超过充分性后继续搜索、同步批次阻塞中途引导；工程上从检查点恢复而非重启 ([anthropic.com/engineering](https://www.anthropic.com/engineering/built-multi-agent-research-system))。LangChain Open Deep Research（LangGraph）是 Scope（用户澄清 → 压缩为研究简报作"北极星"）→ Research（supervisor 派发独立上下文的子代理，结束时压缩为带引用 findings）→ Write（单次 LLM 一次成稿）；关键教训是早期让子代理并行写各章节导致报告割裂，改为只在研究阶段多代理、写作一次成稿 ([langchain.com/blog](https://www.langchain.com/blog/open-deep-research))。Tongyi DeepResearch 的上下文管理是每步只基于"重建的工作区"（问题 + 演进报告 + 最近一次动作/观察）而非全历史，Heavy 模式 BrowseComp 从 43.4 提至 58.3 ([arXiv 2510.24701v3](https://arxiv.org/html/2510.24701v3))。字节 DeerFlow 2.0 是 LangGraph 上的"super agent harness"，HITL 用静态 `interrupt_before/after` 断点、动态中断用 `command.resume`，搜索提供方内置腾讯云 WSA、Tavily、Brave、SearXNG 等，沙箱支持本地/Docker/K8s/E2B ([github.com/bytedance/deer-flow](https://github.com/bytedance/deer-flow))。成本参考：GPT Researcher 约 3 分钟、约 $0.1 一份报告 ([docs.gptr.dev](https://docs.gptr.dev/docs/gpt-researcher/getting-started/introduction))。

PPT 的架构有四条公开路线：模板占位符填充（AiPPT / WPS / 讯飞 / Kimi Classic）、HTML 先渲染再转 PPTX（Gamma / Genspark / Manus 旧管线）、LLM 直写 pptxgenjs / python-pptx / OOXML（Anthropic skill、Claude for PowerPoint、Manus 新管线）、整页图像生成（NotebookLM、Kimi Visual 模式）。最有价值的学术证据是 PPTAgent（EMNLP 2025）：Stage I 分析参考 deck 抽取每页 schema，Stage II 由 LLM 生成大纲（每页配参考页 + 源文档片段）并通过 5 个原子编辑 API（`del_span` / `del_image` / `clone_paragraph` / `replace_span` / `replace_image`）编辑参考页，**页面以 HTML 渲染呈现给模型**而非原始 XML（一页 XML 约 1006 行），动作在 REPL 执行、报错回传最多 2 轮自纠；Qwen2.5 + Qwen2-VL 成功率 95.0%，消融去掉 HTML 渲染降至 74.6%、去掉 schema 降至 78.8% ([arXiv 2501.03936v3](https://arxiv.org/html/2501.03936v3))。它证明了"把品牌/版式约束变成可执行环境而非 prompt 描述"的价值，与 Claude for PowerPoint"读 master 生成"本质相同。开源可参考实现还有 Presenton（Apache 2.0，prompt/文档 → 审阅大纲 → 可复用模板生成 → 结构化画布编辑 → 可编辑 PPTX，REST / MCP / Docker）([docs.presenton.ai](https://docs.presenton.ai/general/overview.md)) 与 SlideDeck AI（LLM 输出 JSON schema → python-pptx 建页）([slidedeckai.readthedocs.io](https://slidedeckai.readthedocs.io/en/latest/usage.html))。推荐的双表示架构是：HTML 作为"给模型看的表示"以保留 LLM 布局能力并用浏览器截图做视觉 QA，OOXML 作为交付格式以避免 Gamma 式导出损失。

海报的架构证据指向同一模式：规划层输出文案 + 版式 JSON（每层内容、位置、字体、颜色、z-order）→ 图像模型只生成背景/主体素材 → 画布引擎合成可编辑文字层与图片层 → 导出并支持按尺寸 re-layout。Canva Craft 是在模型内部拆成规划/渲染两段；CreatiPoster（arXiv 2506.10890）用 RGBA 多模态"协议模型"显式输出每一层的 JSON（内容、字体、字号、x/y/w/h、RGBA、描边、旋转、对齐、行距、字距，层序即 z-order），再由条件背景模型生成背景，支持画布编辑、响应式改尺寸、多语言适配，并开源 10 万张多层设计语料 ([arXiv 2506.10890](https://arxiv.org/abs/2506.10890))；Ideogram Layerize Text API 返回"结构化文字数据 + 去字底图 + 渲染结果"三件套供开发者自建 ([Ideogram: Text Layers](https://ideogram.ai/features/text-layers/))；国内开源的迅排设计（MIT）存两份 JSON（整页 Schema + 扁平元素数组），Vue3 画布、Puppeteer 服务端渲染出图、PSD 导入解析为模板 ([GitHub poster-design](https://github.com/palxiao/poster-design))，是最接近"LLM 产 JSON → 前端画布渲染 → 服务端出 PNG"的现成底座。显式 JSON 比模型内部规划更适合 LingDraft，因为价格/日期校验、品牌约束与多尺寸重排都需要可读写的中间表示。商品保真的稳妥路径是"抠图 → 作为独立图层合成 → 图像模型只生成背景/场景"，这也是美图、稿定、堆友的做法；需要商品进入生成场景时用参考图 + 显式"保持不变"清单，Seedream 4.5/5.0 最多 14 张参考图并建议写明保持不变的部分 ([火山方舟 Seedream 提示词指南](https://docs.volcengine.com/docs/ark/seedream-4-0-5-0-prompt-guide?lang=zh))。

前端与 LangGraph 的衔接有现成协议。AG-UI 用 SSE 事件流推送 `TextMessage*`、`ToolCall*`、`StateSnapshot`（整体替换）与 `StateDelta`（RFC 6902 JSON Patch）、`Activity*`、`Subagent*`，HITL 以 `RunFinished(outcome=interrupt)` 表达 ([AG-UI Events](https://docs.ag-ui.com/concepts/events))；CopilotKit 提供 `useHumanInTheLoop`（LLM 决定何时问，答案作为 tool result 回到 agent）与 `useInterrupt`（图决定暂停，客户端渲染并 resume）两种模式，但其页面标注 "LangGraph (Python) doesn't support Human in the Loop: Interrupts"，选型前必须实测 ([CopilotKit: Human-in-the-loop](https://docs.copilotkit.ai/langgraph/human-in-the-loop))。LangGraph 本身的机制细节决定了节点怎么写：`interrupt()` 通过抛特殊异常实现，恢复时**整个节点从头重跑**（子图作为函数调用时父节点与子图节点都重跑），节点内多个 interrupt 严格按索引匹配、禁止条件跳过或 `while True` 循环，interrupt 前的副作用必须幂等，静态 `interrupt_before/after` 被标注"not recommended for human-in-the-loop" ([LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md))；`HumanInTheLoopMiddleware` 的 `interrupt_mode` 有 `batched`（默认，每个 model turn 一次）与 `per_call` 两种，决策类型为 `approve / edit / reject / respond`，并且必须放在 `ToolRetryMiddleware` 之前否则重试会再次询问 ([LangChain Human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop.md))；进度流式用 `stream_mode="custom"` + `get_stream_writer()` 推送"当前页已更新"粒度的事件 ([LangGraph Streaming](https://docs.langchain.com/oss/python/langgraph/streaming.md))；生产持久化用 `PostgresSaver`，子图有独立 checkpoint namespace、跨子图共享要走父图 state 或 Store，长会话 checkpoint 会累积需清理策略 ([Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers.md))。安全上，OpenAI Agents SDK 与 Vercel AI SDK 都警告客户端可伪造审批，Vercel 用 HMAC 绑定 tool name + call id + input，Microsoft Agent Framework 默认把审批响应绑定到同一 session 的 pending request ([AI SDK: Tool Approvals](https://ai-sdk.dev/docs/agents/tool-approvals); [MS Agent Framework](https://learn.microsoft.com/en-us/agent-framework/tutorials/agents/function-tools-approvals))。

中文信源是调研场景的硬约束。国内可合规使用的 Web Search API 以博查为代表（面向中文、数据不出境，提供语义重排）([ai-bot.cn](https://ai-bot.cn/sites/76040.html))，秘塔搜索 API 每次查询 0.03 元并提供网页全文获取 ([AIbase 2025-07](https://news.aibase.com/zh/news/19928))，腾讯云 WSA 需在控制台开通 ([cloud.tencent.com 文档](https://cloud.tencent.com/document/product/1552/132746))；海外 Parallel / Tavily / Exa 约 $1–15 每千次，但互相引用的 benchmark 全为供应商口径 ([parallel.ai](https://parallel.ai/articles/openai-web-search-vs-parallel-vs-exa-vs-tavily-how-to-choose))。微信公众号内容没有官方对外搜索 API，搜狗微信搜索的订阅号、关键词功能已下线 ([钛媒体](https://www.tmtpost.com/2578037.html))，腾讯自家产品（元宝 / ima / WorkBuddy）是唯一有合法公众号信源的路径 ([IT之家 2026-06-15](https://www.ithome.com/0/964/468.htm))。因此"用户补充信源（上传 PDF、粘贴链接/全文）"应是调研场景的一等 HITL 入口，产品不应承诺自动获取艾瑞、企查查类数据。

把以上先例映射到 LingDraft 的 LangGraph 图，可得到一组有明确出处支撑的检查点：

## 结论

这轮调研改变了两个判断。第一，WorkBuddy 不应被当作一个整体来对标，而应拆成三条路径分别对标：它的 PPT 流程（条件追问 + 元素级局部修改 + 原生 .pptx）已经是国内最好的样板，值得在 LingDraft 的 PPT 场景直接复刻并在"数字锁定"和"引用进备注"上超越；它的海报路径分裂为"Ardot 可编辑画布"和"通用 Agent 写 HTML 截图"两种，后者的 3–4 轮排版返工与缓存旧图问题恰恰证明海报不能用 HTML 当画布；它的深度研究只是技能包，没有任何研究 UX 可参考，LingDraft 的调研场景应直接对标 Kimi、秘塔、天工与 LangChain Open Deep Research。第二，Sean 在黑五海报案例里看到的"先问风格"大概率是模型即兴行为而非产品承诺，这反过来说明 LingDraft 的差异化不在"会不会问"，而在"问得确定"——澄清由状态里缺失的高返工成本字段驱动，同一需求每次都得到同样的检查点。

真正没有竞品占住的位置有三个，而且三个都能从同一个设计决策派生：把关键信息（价格、日期、规则、数据点、论断及其来源）从一开始就作为结构化字段存在 LangGraph state 里，而不是散落在 messages 或像素中。有了这个中间表示，海报的文字层校验与合规词检查、PPT 的"原文模式"与引用进讲者备注、调研的事实/推断分层与 URL 可达性校验，都只是同一份数据的不同渲染；"研究 → PPT → 海报"的跨场景复用也只需三个子图共享一个持久化的 `research_brief`，而不是把全文塞回上下文。需要诚实面对的不确定性是：没有任何单一产品完整实现过这套多检查点组合，也没有定量证据说明用户会不会把它视为负担——Mavis 因"停下来确认"被抱怨，LangChain 指出用户不愿为简单问题等 10 分钟；所以默认路径必须快，每个检查点都要可被用户设置为自动通过，并以 WorkBuddy 的"模糊需求出空洞内容"和 NotebookLM 的"修订即全量重生成"作为两条明确的反面红线。
